# agent-compose — Product Requirements Document

**Status:** Draft v0.9
**Author:** moldy
**Last updated:** 2026-08-14

---

## 1. Vision

`agent-compose` is a declarative YAML DSL for defining agent graphs, compiled to executable LangGraph code. It is to agent graphs what `docker-compose` is to containers and what Terraform is to infrastructure: a human- and agent-writable specification layer that separates *what the graph is* from *how it runs*.

The DSL serves two audiences simultaneously:

1. **Developers**, who get a compact, diffable, reviewable representation of agent systems.
2. **Coding agents**, who can author and modify graph definitions at a fraction of the token cost of raw framework code, with a fast validation loop (`agent-compose validate`) that surfaces errors in milliseconds instead of runtime stack traces.

## 2. Problem

Building multi-agent systems today means writing imperative framework code (LangGraph, AutoGen, CrewAI). This has recurring costs:

- Graph structure is buried in code; reviewing "what changed in the topology" requires reading router functions and state mutations.
- Coding agents burn tokens generating and re-generating boilerplate, and get error feedback late (at runtime) rather than early (at validation).
- Definitions are not portable across deployment shapes: local prototype vs. distributed/isolated cloud execution requires structural rewrites.
- Routing decisions made by LLMs are opaque runtime behavior rather than inspectable data.

Prior art validates the declarative direction but leaves gaps:

- **Oracle Agent Spec** (arXiv 2510.04173): strong component model (control-flow vs data-flow edges, `$component_ref`), but a configuration format without executable control-flow semantics; memory/datastores punted to roadmap.
- **PayPal's declarative DSL** (arXiv 2512.19769): production-proven (60% dev-time reduction, sub-100ms orchestration overhead), JSON IR + static analysis, tools-as-pipelines — but DAG-only and enterprise-internal.
- **duckflux**: excellent minimal YAML ergonomics, CEL expressions, first-class error policy — but workflow-oriented, not agent-graph-oriented, and runtime-coupled rather than compile-to-framework.
- **LangGraph**: the right runtime primitives (cycles, checkpointing, subgraphs, `Send`, `RemoteGraph`) but no declarative authoring layer.

`agent-compose` combines: Agent Spec's component/edge model, PayPal's compile-to-IR + static analysis, duckflux's CEL + error-policy ergonomics, and LangGraph as the execution substrate.

## 3. Goals

- **G1.** A YAML DSL expressing agent graphs: agent defs, tool defs, deterministic nodes, edges (including cycles), shared state, and structured I/O.
- **G2.** A compiler pipeline, shipped as a single Rust binary: multi-file YAML → resolved, validated flat IR → deterministic LangGraph (TypeScript) codegen.
- **G3.** Validation as a first-class product: reference checking, schema compatibility across edges, routing exhaustiveness, cycle-termination proofs — all pre-runtime, with LSP-quality error messages.
- **G4.** Deterministic routing over model-produced values ("the LLM decides the value; the interpreter decides the transition").
- **G5.** Forward-compatible grammar for cloud/distributed placement (parsed from day one, executed later).

## 4. Non-Goals (v0)

- Building a bespoke runtime. LangGraph is the execution engine; we emit code, we do not interpret.
- Graph structure optimization/learning (GPTSwarm/AFlow-style). The DSL may later become a *target* for generated graphs, but v0 is hand/agent-authored.
- Visual editor.
- Multi-language codegen targets (a Python backend is a candidate for v2; TypeScript first).
- Executing the `placements` section (reserved keywords only in v0).

## 5. Core Design Decisions (settled in research phase)

### 5.1 Multi-file composition — explicit, Terraform-style

- Layout: `main.yml` + `agents/*.yml`, `tools/*.yml`, `flows/*.yml`, `state.yml`, `deploy.yml`.
- **Explicit imports** in `main.yml` — no directory scanning. "What is in this graph" must be unambiguous, and multiple entrypoints may share a definitions library.
- **Typed global address scheme**: `agent.researcher`, `tool.web_search`, `flow.review_loop`. References are type-checked ("this edge expects an agent, you gave it a tool").
- **Flows are modules**: a subgraph declares an input/output schema; its I/O surface is interchangeable with a tool's, so flows are callable as tools by agents (the Agent Spec / PayPal recursion). Instantiable with bindings like Terraform modules. Both call sites run: a `flow:` node instantiates deterministically, and a `flow.*` in an agent's `tools:` instantiates once per model tool call — under the instance identity §9.19 fixes and joined to the trace the way §9.20 fixes, with the flow's `inputs`/`outputs` as the tool's parameter/result schemas.
- The compiler resolves all files into **one flat IR artifact** (JSON): the diffable, versionable deploy artifact. Multi-file is authoring UX; the runtime/codegen sees a single resolved document.

### 5.2 Structured I/O — mandatory outputs, optional inputs

- **Every agent must declare an output schema** (JSON Schema). This is load-bearing for routing (5.3) and for distribution (5.7: every edge is serializable).
- Input schemas optional; default is string-in for entrypoint agents (duckflux's "string by default, schema opt-in").
- Codegen emits Zod schemas for state typing and reply parsing. The schema a provider is *constrained by* is the compiler's own JSON-Schema lowering — the same column the reply is parsed against — sent on the wire directly rather than through `withStructuredOutput`, whose Zod→JSON-Schema conversion silently drops constraints (§9.16).

### 5.3 Routing — runtime always routes; the question is who produced the value

The central reframe: even "agent-decided" routing is reified as a field in the agent's structured output (e.g. `next: enum[approve, revise, escalate]`). Edges carry optional CEL guards over the source node's output. The LLM decides the **value**; the compiled router decides the **transition**.

Consequences:
- The runtime stays fully deterministic (LLMs are unreliable routers: they forget steps, miscount iterations, skip transitions — duckflux thesis, Temporal replay requirement).
- Routing decisions appear in traces as data, not opaque model behavior.
- **Exhaustiveness checking**: enum with 3 variants + node with guarded edges + optional default → compile error if any variant is unroutable. No existing framework offers this.
- "Agent-routed" and "logic-routed" collapse into one mechanism; the guard simply references either a model-produced field or a computed one.

### 5.4 Cycles — allowed, with statically verified termination

Loops are prominent (evaluator-optimizer, ReAct, plan-revise); DAG-only loses. Design:
- Back-edges permitted in flow graphs.
- **Every cycle must carry a termination guard**: `max_iterations` and/or a CEL exit condition on at least one edge in the cycle.
- Compiler detects cycles (Tarjan SCC) and **rejects any SCC with no bounded edge**.
- Codegen emits an iteration counter into graph state per bounded cycle.
- Iteration boundaries are natural checkpoint/resume points.

### 5.5 Node taxonomy

| Node type | Semantics | Codegen |
|---|---|---|
| `agent` | LLM call with structured output; the tool-call loop is bounded by `max_tool_iterations` (default 8, §9.14), and a tool call the contract *refuses* returns to the model as a tool error rather than failing the node, spending one of that bound (§9.22) | node fn + Zod schema + structured output |
| `exec` | shell command (map input → env vars; string input → stdin) | child-process wrapper |
| `http` | HTTP request | fetch wrapper |
| `function` | host-registered function by name (escape hatch; breaks spec portability — documented) | registry lookup |
| `flow` | subgraph instantiation; also an agent's tool, one instance per model tool call (5.1, §9.19) | separate compiled graph, invoked per instantiation (§9.17) and per flow-as-tool call, whose instance joins the trace as a dispatch record (§9.20) |
| `map` | fan-out over an agent-produced collection, homogeneous or discriminator-routed (see 5.6) | in-task dispatch inside the map node (§9.17) |
| `human` | human-in-the-loop pause: input schema (what the human sees), output schema (what they return, routable like any structured output), `timeout` + `on_timeout` route | the node's task parks on a promise an answer settles — the app's resume route, or a terminal `run`'s prompt (M2; **not** LangGraph `interrupt()` — see resolved q4, q21) |

**Tool vs function — separate keywords (settled).** `tools:` on agent defs (LLM-discovered, nondeterministically selected, requires an LLM-facing description) and `function` as a node type (graph-invoked, deterministic, args checked against a signature) stay distinct: they differ in call semantics, validation, and trace semantics. The *definition* is unified — a single `tool.web_search` component can be attached to an agent's tool list and invoked as a function node (Agent Spec's def/use split).

Temporal-inspired discipline: the compiled graph is the *workflow* (deterministic, replayable); nodes are *activities* (effectful, retryable). Per-node `retry` / `timeout` / `on_error` policy is declared in YAML with duckflux's resolution chain: flow override > node > defaults > fail. Strategies: `fail`, `skip`, `retry` (exponential backoff), `fallback: <node ref>`.

The spec never contains executable code (Agent Spec's security posture). Code logic lives in three layers:
1. **CEL expressions** for conditions and mappings — non-Turing-complete, sandboxed, type-checked at parse time.
2. **First-class control constructs** in YAML: guarded edges, bounded loops, `map` fan-out, `when` guards.
3. **Escape hatches**: `exec`, `http`, `function` — implementation outside the spec, referenced by identifier.

CEL implementation choice (v0): the compiler parses and type-checks expressions with the Rust CEL implementation (`cel` crate); generated routers embed a JS CEL evaluator rather than transpiling CEL→TS. Two interpreters means a semantic-drift risk between `validate` and runtime — mitigated by a shared conformance fixture corpus run against both in CI. Transpilation is a later optimization.

### 5.6 Fan-out — agent-controlled cardinality, deterministic dispatch

The routing reframe (5.3) extends from *which edge* to *how many instances* and *which destination per item*. An agent never spawns work directly; it emits an **array in its structured output**, and the `map` construct dispatches over it deterministically. Cardinality and destination are data.

**Homogeneous fan-out:**

```yaml
nodes:
  plan: { agent: agent.planner }        # output.tasks: array, max_items: 20
  work:
    map:
      over: plan.output.tasks           # CEL path to the array
      as: task                          # per-instance input binding
      node: agent.worker                # any node ref, including flow.* subgraphs
      max_concurrency: 5
      on_item_error: skip               # fail | skip | retry per item
```

**Heterogeneous fan-out (per-item routing)** — motivating case: a bug-triage agent sends some findings to fixer agents and others to a manual-review queue. Items are a **tagged union** with a discriminator field; the map routes on it:

```yaml
agent.triage:
  output:
    findings:
      type: array
      max_items: 50
      items:
        discriminator: kind
        variants:
          auto_fixable: { file: { type: string }, patch_hint: { type: string } }
          needs_human:  { summary: { type: string }, severity: { enum: [low, high, critical] } }

nodes:
  dispatch:
    map:
      over: triage.output.findings
      route_by: kind
      routes:
        auto_fixable: { node: agent.fixer, max_concurrency: 5 }
        needs_human:  { node: tool.review_queue }   # sink route: enqueue via http/function
```

Rules and guarantees:

- **Bounding is mandatory** (mirrors the SCC cycle rule): `max_items` on the source array schema (enforced at structured-output validation — the model cannot return more) plus `max_concurrency` at execution. An unbounded fan-out is a compile error.
- **Exhaustiveness per variant**: every discriminator variant must have a route or an explicit `default:` — compile error otherwise. The agent structurally cannot produce an unroutable item.
- **Schema narrowing**: each route's target node is validated against its variant's payload shape only (discriminated-union narrowing; Zod discriminated unions in codegen), not a lowest-common-denominator item type.
- **Join via reducers**: instances run in isolated item-scoped contexts; writes to shared state must target channels with a declared `reduce` policy (`append`, `merge`, `last_wins`). Writing to a non-reduced channel from inside a `map` is a compile error. The downstream edge is the barrier: it fires when all instances complete, per `on_item_error` policy.
- **Deterministic ordering**: completion order is nondeterministic, so appended results are automatically index-tagged and reordered by source-item index before the join. Unordered reduces would silently break replay.
- **Sink routes and `detach`**: routes may target non-compute sinks (queues, webhooks, ticketing — this is how agent graphs talk to non-agent infrastructure). Default join semantics wait on *all* routes, including sinks (a failed enqueue is a surfaced failure). Per-route `detach: true` opts into fire-and-forget; detached routes cannot write to reduced state (compile error). **Replay interaction (settled)**: the design is idempotency-key delivery — an `idempotency_key` derived from `execution_id + node + item_index` is passed to the sink automatically, and sinks are documented to dedupe on it. The v0 implementation restricts: `detach` + checkpointing enabled is a validation error pointing at the roadmap (outbox-pattern delivery is not v0 work).
- **`route_by` is a literal discriminator field in v0**, not an arbitrary CEL expression — this keeps exhaustiveness checking decidable and the agent's contract legible in its schema. CEL-routed maps are a possible later escape hatch that forfeits exhaustiveness (mandatory `default:`).
- **Codegen**: one construct — the map node dispatches instances inside its own task with a bounded-admission scheduler (§9.17); reducer channels get standard LangGraph reducers with index-tagged, source-order folding; the map node's completion is the join. Heterogeneous is homogeneous with a lookup table.
- **Placement synergy**: map instances are the natural unit for `runtime: isolated` (5.10) — one worker per sandbox with zero change to the logical definition.

### 5.7 State — three tiers

1. **Node-scoped I/O**: typed inputs/outputs per node.
2. **Shared graph state**: a `state:` section generates the LangGraph state schema (`Annotation` channels, Zod-typed) with per-channel reducers. Default wiring is name-based (outputs write channels of the same name — Agent Spec's optional-data-edge insight). Subgraphs receive parent state only through explicit bindings (PayPal's `passVariables` discipline).
3. **Conversation history**: an implicit append channel available to agent nodes. **Scoping (settled): isolated by default across subgraph boundaries** — a flow's behavior must not depend on the caller's conversation, or reusability and the flow-as-tool equivalence break. Opt-in `context: inherit` on the flow-node instantiation for genuine continuation cases. Nothing crosses a module boundary implicitly.

**Data-edge syntax (settled): deferred.** Full explicit data edges are not in v0. Instead, a per-node `writes:` remapping (`writes: { summary: reviewer_summary }`) covers the two real failure modes of name-based wiring — channel collisions between nodes and renames across subgraph boundaries — at a fraction of the grammar cost. Full data edges remain an additive later feature if demand appears.

Persistence of *execution state* is the journal's (resolved q26–q27: SQLite locally, Postgres as the distributed slot — the checkpointer this sentence once named was rejected by resolved q26). Durable *attachable* storage — the cross-session memory and datastore story the literature punts on — is first-class: see 5.8.

### 5.8 Attachable storage — stores as first-class components

Graph state (5.7) is execution state. **Stores** are durable, attachable storage resources — the concrete answer to cross-session memory and datastores, which the surveyed prior art uniformly defers.

```yaml
store.user_prefs:
  kind: kv
  value_schema: { theme: { type: string }, verbosity: { enum: [low, high] } }
  scope: session

store.docs:
  kind: vector
  embed: { model: text-embedding-3-small }
  metadata_schema: { source: { type: string } }
  scope: global
```

- **Address scheme**: new `store.*` namespace; def/use split as everywhere else. Kinds in v0: `kv`, `vector`, `blob`. Relational/SQL is deliberately excluded — it drags query-language semantics into the spec; a `function` node wrapping a DB client is the escape hatch.
- **Two consumption modes** (mirrors tool vs function, 5.5):
  1. *Agent-attached* — `stores: [store.docs]` on an agent def; codegen synthesizes LLM-facing tools from the store's schema (`docs_search`, `user_prefs_get/set`). Nondeterministic, agent-invoked, recorded as tool calls.
  2. *Store-op nodes* — `{ store: store.user_prefs, op: get, key: state.user_id }`. Deterministic, graph-invoked (load context before an agent, persist after). Same definition, two usage surfaces, surface-specific validation.
- **Least-privilege attachment (§9.13)**: a `stores:` entry may declare `agent_access: read` (default `read_write`) to withhold the synthesized write tools from the model — the store-tool counterpart of placement isolation's blast-radius containment.
- **Scope**: `execution` (dies with the run) | `session` (persists across executions sharing a session key) | `global`. **Triggers supply session identity**: a trigger may declare `session_key: <CEL over payload>`; all session-scoped stores — and conversation history — key off it. Cross-session memory = session-scoped store + trigger-supplied session key, declaratively.
- **Backend binding (settled — alias-only)**: a store optionally declares `backend: <alias>` — a bare string naming an abstract slot, never provider config. All physical configuration lives in the per-target deploy layer:

  ```yaml
  # stores/docs.yml — logical, env-invariant
  store.docs:
    kind: vector
    scope: global
    embed: { model: text-embedding-3-small }
    backend: docs_db            # abstract alias; omit to use the kind default

  # deploy/staging.yml                 # deploy/prod.yml
  storage_backends:                    storage_backends:
    defaults:                            defaults:
      kv: { provider: redis, url: ${REDIS_URL} }
    aliases:                             aliases:
      docs_db:                             docs_db:
        provider: chroma                     provider: pgvector
        url: ${CHROMA_URL}                   url: ${DOCS_DB_URL}
  ```

  - **Resolution**: explicit alias → per-kind `defaults:` → target built-in. `--target local` substitutes SQLite/local disk for every store unconditionally — the zero-infra guarantee.
  - **Per-target invariant**: `--target <name>` loads `deploy/<name>.yml`. Only the deploy layer (storage_backends, placements, event_sources) forks per environment; `agents/`, `flows/`, `stores/`, `tools/` never do. Terraform-workspace discipline: env differences live in one layer.
  - **Compile-time validation**: provider config blocks are checked against provider-published schemas; an alias referenced by a store but undefined in the active target is a compile error naming the target; capability checks (e.g. `vector` store → vector-capable provider) apply at the alias definition. Provider config takes `${ENV_VAR}` references only — the spec never contains credentials (syntax checked at `validate`; presence checked at launch — see 5.9).
  - Rejected alternatives, for the record: address-keyed override maps in deploy.yml (action-at-a-distance) and inline provider config on stores (bakes env-specific choices into logical files, forking them per environment).
- **Replay discipline**: store ops are effects (activities). Reads are recorded — replay consumes history, not the live store. Writes are at-least-once with idempotency keys derived from `execution_id + node + item_index` — the **execution-derived idempotency key** principle again (detach sinks 5.6, event dedupe 5.11, callback delivery resolved q35) — a named cross-cutting rule.
- **Compile checks**: schema-checked ops against `value_schema`/`metadata_schema`; store writes inside a `map` require an item-derived key or a keyed `kv` write — unkeyed blob/global writes from concurrent instances are a validation error; `session`-scoped store usage in a flow with no session-keyed trigger is a validation error.

### 5.9 Providers & models — LLM configuration as first-class components

Two namespaces with the usual def/use split, because the layers change for different reasons: **`provider.*`** holds *connection* (kind, base_url, key ref), **`model.*`** holds *behavior* (model id + settings). Agents reference only `model.*`; swapping a project from hosted to local inference is a one-line provider edit.

```yaml
# providers.yml
provider.anthropic:
  kind: anthropic                  # plugin: anthropic | openai | openai_compatible | bedrock | ...
  api_key: ${ANTHROPIC_API_KEY}

provider.local:
  kind: openai_compatible          # ollama, vllm, proxies
  base_url: ${LOCAL_LLM_URL}
  api_key: ${LOCAL_LLM_KEY}

# models.yml
model.smart:
  provider: provider.anthropic
  id: claude-sonnet-4-6
  settings:                        # validated against the provider plugin's schema
    max_tokens: 8000
    thinking: { budget_tokens: 4000 }

model.fast:
  provider: provider.anthropic
  id: claude-haiku-4-5
  settings: { temperature: 0.2 }

model.default:
  route: [model.smart, model.fast]   # ordered fallback
  route_on: [rate_limit, overloaded, timeout]
```

- **Provider-specific settings**: each provider `kind` plugin publishes a settings schema; `settings:` blocks are compile-checked against it (`thinking:` on an OpenAI provider → validation error at the model def). Same mechanism as storage provider config (5.8).
- **Capability checking**: agents require structured output (5.2), so every referenced model's provider must declare structured-output/tool-use capability — an agent bound to a model that cannot honor the contract is a compile error.
- **Routes**: a `model.*` is either a direct binding or an ordered `route:` with `route_on:` failure conditions (rate limit, overload, timeout). Failover is deterministic runtime behavior recorded in the trace ("served by model.fast, fallback #1"). Route members are validated for capability equivalence so a fallback cannot silently break structured output. Content-based routing is explicitly out of scope — that is what graph edges are for.
- **No inline settings overrides on agents** — the backends lesson (5.8): one binding form. Different settings ⇒ define another named model. Every LLM configuration in a project stays greppable in one file; codegen stays deterministic.
- **Providers are logical-layer, not per-target**: unlike storage backends, providers rarely differ structurally per environment (same Anthropic everywhere; keys/URLs vary via env refs). The alias mechanism exists to extend if a real case appears; not pre-built.

**Secrets** (extends the credentials rule of 5.8):
- Config takes `${ENV_VAR}` references only, never literals. **Env refs survive into the IR unresolved** — resolution happens at process start in generated code, never at compile — so the flat IR stays committable/diffable and generated code never contains a key.
- `validate` and `build` check ref syntax only — an artifact must be buildable anywhere, including CI boxes holding no secrets (least-privilege distribution in 5.10 depends on this). Presence is a launch-time check: generated code verifies its environment at process start, and `run`/`serve` fail fast before invoking the graph, naming the missing variable (§9.15).
- **Least-privilege distribution**: under `--target distributed` (5.10), an isolated node's deployment receives only the env vars its resolved providers/backends reference — computable statically from the IR, since every secret is a named ref. Blast-radius containment for keys falls out of the design.

### 5.10 Cloud & distribution — placement annotations, not distributed edges

Logical definition and placement are orthogonal (Kubernetes/Terraform lesson):

```yaml
# deploy/<target>.yml — selected by --target <name>; see 5.8 per-target invariant
hub:
  join_token: ${MESH_JOIN_TOKEN}   # required when placements exist (resolved q38)
placements:
  mac:
    members: [agent.signer]        # claimed at join by whoever has the keys
  gpu:
    members: [agent.embedder]
```

- `--target local`: one Node.js process.
- `--target distributed`: **hub-and-spoke** — one hub owns the graph (scheduler, journal, wait board, triggers); workers execute the nodes placed on them over an outbound-dialed dispatch protocol (resolved q37, q43). The earlier sketch here — N deployable LangGraph apps stitched with `RemoteGraph` — is superseded by resolved q43: the journal, wait board, and instance identity live outside LangGraph's state model, so the seam RemoteGraph offers is the wrong one.
- Already-guaranteed properties make this nearly free: structured I/O on every node ⇒ every edge is serializable ⇒ any edge can become a network boundary without semantic change; the journal (resolved q26) ⇒ one durable execution history whoever executes.
- Isolation is also a **security** feature (per-agent sandboxing, credentials, blast-radius containment for tool-wielding agents) — a declarative story no current framework has.
- Placements are **named claims** (resolved q38): a placement is a logical name with `members:`, and a worker asserts it at join — the address-keyed `runtime: isolated|colocated` shape this section once sketched was reserved grammar and is re-shaped by the same resolutions.
- `placements` executes under the distributed runtime (resolved q37–q44); until that lands it stays parsed and validated only.

### 5.11 Invocation & triggers — how executions come to exist

The logical graph defines *what runs*; **triggers** define *what causes an execution to exist*. A trigger is a (source, input binding, response mode) tuple declared in a `triggers:` section. This generalizes `entrypoint`: a project may declare multiple triggers targeting different flows — the entrypoints of a project are exactly the flows that triggers point at.

```yaml
# triggers.yml
triggers:
  cli:
    type: manual                      # implicit for every flow; shown for clarity
    flow: flow.review_loop

  on_request:
    type: http
    flow: flow.review_loop
    input:
      goal: payload.body.goal         # CEL over the trigger payload
    respond: async                    # sync | async
    callback: payload.body.callback_url   # optional completion webhook (async only)

  nightly:                            # reserved grammar in v0 (the `placements` move)
    type: schedule
    flow: flow.triage
    cron: "0 3 * * *"
    input: { scope: "'full'" }
```

Rules and semantics:

- **Input binding is compile-checked**: trigger `input:` mappings are CEL over the trigger payload, validated against the target flow's input schema — the same machinery as edge schema compatibility. A trigger that can produce an input the flow can't accept is a compile error.
- **`manual`** (v0): CLI/SDK invocation — `agent-compose run <flow> --input k=v`. Implicit for every flow with an input schema.
- **`http`** (v0): the graph as an endpoint. `respond: sync` blocks and returns the flow's output (only sane for fast graphs); `respond: async` (default) returns an execution id immediately, with an optional `callback:` webhook that fires on lifecycle events — each parking that opens pauses, and settle (resolved q34) — signed and allowlisted per resolved q33, delivered at-least-once from the journal per resolved q35. Async is the natural pairing with durable execution.
- **`schedule`** and **`event`** (queue/subscription): reserved grammar in v0 — parsed and validated, no-op. Implementing them means owning a scheduler/consumer process (M3 territory), and event-backend plurality (SQS, Redis streams, NATS…) is a design project of its own. Webhook-style events need neither: with inbound auth, lifecycle webhooks and durable delivery, the `http` trigger is the webhook story end to end, so these two kinds stay reserved for the sources HTTP cannot speak for — the clock, and pull-style queues (resolved q36).
- **Resume is an invocation.** With `human` nodes (5.5), an interrupted execution must be able to receive the human's response. The generated invocation surface therefore has two verbs — `start(flow, inputs)` and `resume(execution_id, payload)` — and the `http` trigger exposes both. Resume payloads are validated against the interrupting `human` node's output schema. This unifies triggers with the HITL story rather than bolting on a separate callback mechanism. The **status** route carries the question as well as the state: an `interrupted` report lists the pauses the execution is holding, each with what the human is shown, the schema their answer is validated against, and the URL that takes it — so a UI is built from the report rather than from the composition. An execution may hold more than one pause (a `map` over a flow that pauses), so a resume names which one it answers; a payload that fails validation does not consume the wait.
- **An answer has a second delivery surface: the terminal (settled, §9.21).** `agent-compose run` at a terminal renders each pause it reaches and reads the answer from standard input, holding it to the same `output:` schema against the same wait board — so a manual-trigger-only flow with a `human` node in it is completable without an app. It is the *delivery* that differs and nothing else: which pause an answer addresses, what refuses it, and what the trace records are decided once for both surfaces. A run with no terminal (and `AGENT_COMPOSE_INTERACTIVE=0`, which forces it) keeps reporting the pause and exiting `3`.
- **`event` backends (settled)**: the grammar is backend-agnostic — a trigger declares a logical `source:`; an `event_sources:` config section binds logical names to infrastructure (Redis Streams, SQS, NATS, …), mirroring `placements`' logical-vs-infra separation. Backends implement a minimal consumer contract (subscribe → payload stream + ack/nack) via a plugin interface. Delivery is at-least-once with inbound dedupe on message id — symmetric with the outbound `detach` idempotency-key design (5.6). The interface plus one blessed reference backend (Redis Streams) ship when a pull source is actually needed — behind the http-native events pass (resolved q36); further backends are plugins.
- **`respond: sync` (settled)**: sync is a compile-time-constrained mode. A flow exposed via `respond: sync` must be **statically interrupt-free** — no `human` node reachable from its entry, no wait-style constructs — enforced by graph reachability analysis (same static machinery as SCC and exhaustiveness). Sync triggers require a `timeout:` (default 60s); on expiry the response **upgrades to async** (HTTP 202 + execution id + status URL) while the execution continues durably — nothing cancelled, no work lost. Node retries consume the timeout budget with no special casing.
- **Codegen**: `manual` → the `run` CLI; `http` → a generated Fastify app wrapping the compiled graph (start / resume / status routes), reusing the same generated Zod schemas for payload validation. Auth on `http` triggers was deliberately out of scope for v0 (deploy behind your own gateway); the declarative story is now resolved q32/q33 and ships with the http-native events pass (§7 M3).

### 5.12 Compiler contract

- **Generated code is a build artifact, never hand-edited.** The DSL is the single source of truth.
- **Deterministic codegen**: same DSL → byte-identical output (stable ordering), so regeneration diffs are meaningful.
- **Eject path**: for graphs that outgrow the DSL, copy generated code out and own it (CRA model).
- **Pinned backend versions**: each compiler release targets a pinned LangGraph (JS) version; upgrades are explicit and versioned, like Terraform providers. DSL semantics must never drift silently with upstream API churn.
- **Toolchain split (settled)**: the compiler/CLI is a single static Rust binary — parse, resolve, validate, and codegen carry no language-runtime dependency, which keeps `validate` in the millisecond budget and makes the toolchain installable anywhere a coding agent runs. A JavaScript runtime is required only to execute generated output.
- **Generated-artifact runtime (settled)**: that runtime is **Bun** by default — the documented install (`bun install`), launch (`bun src/index.ts`), and type gate (`bun run typecheck`) of every emitted project, and what `run`/`serve` and CI use. **Node.js >= 22.18 is a supported fallback**, declared in the emitted `engines.node` and kept honest by two gates: one installs a golden with npm and type-checks, constructs and runs it under Node, and one answers both shared conformance corpora — the schema table's Zod column and the CEL corpus — with that engine, since a `format:` regex and the emitted evaluator's arithmetic are the engine's rather than the emitted code's. Generated code itself is runtime-neutral: no `Bun` global, no `bun:` specifier, no import outside the pinned set — a static gate over the whole golden corpus, not a convention (§9.18).
- **Release distribution (settled)**: a tagged commit is the release. `v<version>` builds four artifacts — Linux `x86_64` and `aarch64` against **musl**, macOS `x86_64` and `aarch64` — each an `agent-compose-<version>-<target>.tar.gz` holding the one binary, published with a single `SHA256SUMS` over all four; the repository's `install.sh` verifies a download against it and installs nothing the checksum does not vouch for. musl rather than glibc because the single-binary promise is about *where it runs*: the job asserts static linkage rather than trusting the target name. The tag must equal the crate version, and `--version` carries the crate version, the short commit and the target triple, so a binary that was downloaded rather than built can say which build it is. The build, check and package steps are a callable workflow that a pull-request dry run calls with no tag and no publish, so the pipeline is exercised before the day it must not fail (§9.24).

## 6. Example (illustrative sketch, not final grammar)

```yaml
# main.yml
version: "0.1"
imports:
  - providers.yml
  - models.yml
  - agents/researcher.yml
  - agents/reviewer.yml
  - tools/web_search.yml
  - flows/review_loop.yml
  - triggers.yml            # see 5.11 — entrypoints are the flows triggers target

state:
  draft: { type: string }
  feedback: { type: string }

# agents/reviewer.yml
agent.reviewer:
  model: model.smart              # see 5.9 — no inline provider/settings
  tools: [tool.web_search]
  output:
    verdict: { enum: [approve, revise] }
    feedback: { type: string }

# flows/review_loop.yml
flow.review_loop:
  inputs:  { goal: { type: string } }
  outputs: { draft: { type: string } }
  nodes:
    write:  { agent: agent.researcher }
    review: { agent: agent.reviewer, retry: { max: 2, backoff: 5s } }
  edges:
    - { from: start, to: write }
    - { from: write, to: review }
    - { from: review, to: write,
        when: "review.output.verdict == 'revise'",
        max_iterations: 3 }          # termination guard on the cycle
    - { from: review, to: end,
        when: "review.output.verdict == 'approve'" }
```

Validator guarantees for this file: all refs resolve and are correctly typed; `verdict` routing is exhaustive (`revise` and `approve` both routed; compile error otherwise); the write↔review cycle is bounded; edge payloads are schema-compatible.

## 8. Risks

| Risk | Mitigation |
|---|---|
| LangGraph API churn breaks codegen | Pin backend version per release; explicit versioned upgrades; golden-file tests per pinned version |
| LangGraph JS lags LangGraph Python on needed primitives (`Send` — `interrupt` and `RemoteGraph` left the needed set: resolved q4, q43) | Primitive-parity audit as part of each pinned-backend upgrade; required primitives exercised by the e2e harness |
| DSL expressiveness ceiling → users bypass it | `function` escape hatch + `eject`; treat repeated ejects as grammar feedback |
| Hand-edited generated code forks source of truth | Generated-file headers, `build --check` in CI, docs discipline |
| CEL semantic drift between Rust validator and JS runtime | Shared conformance corpus run against both interpreters in CI; both implementations pinned per compiler release |
| Scope creep toward bespoke runtime | Hard non-goal; LangGraph owns execution |

## 9. Resolved Questions (log)

Formerly open, now settled — rationale lives in the referenced sections:

1. **Data edges** → deferred; per-node `writes:` remap ships in v0 (5.7).
2. **Conversation-history scoping** → isolated by default; opt-in `context: inherit` (5.7).
3. **Tool vs function** → separate keywords, unified definitions (5.5).
4. **Human-in-the-loop** → `human` node type in v0 grammar; runtime landed in M2, and it **parks a promise rather than calling LangGraph's `interrupt()`**. Two properties of the shaping decide it. `interrupt()` resumes a run from a checkpointer, which this release does not configure — durable execution is M3 — so it would buy nothing the parked promise does not, at the cost of a durability story the runtime cannot honour; and it announces itself out of the *top-level* stream, while map instances and `flow:` subflows run inside their node's own task as separate runs of separately compiled graphs (resolved q17), so a pause two instances down would have to be lifted through two run boundaries built to keep their instances' business inside them. Parking leaves the pause where it happened. What follows is the M2 durability boundary, stated in the emitted `README.md` and in grammar §8.7: a wait lives in the serving process, and a `serve` restarted while a human was thinking has lost it. Making waits survive a restart is durable execution's job (M3), and is the one thing a checkpointer-based shaping would then be reconsidered for (5.5, 5.11).
5. **Spec versioning** → required `version:` field; semver on the spec; compiler declares a supported range; breaking changes gated behind a major bump + `agent-compose migrate` codemod; old syntax is never silently reinterpreted — refuse and say what the reader must do. Pre-1.0, minor bumps may break with a migration provided. **Amended in M2 (resolved q23), and only about the message**: the refusal named `agent-compose migrate`, a verb no build has shipped, which G3 makes worse than saying less — a reader who acts on the help line meets a usage error, and the discovery surface's own bind (registry ⊇ documents) refuses a document that names a verb clap does not have. Until the codemod ships, the refusal names the versions this build accepts and says the port is of *syntax*, not of one field; the codemod commitment is unchanged and the message names it when there is one to name. `docs/grammar.md` §1.3 states the same thing where an author meets it.
6. **`detach` under durable execution** → idempotency-key design, v0 restriction (5.6).
7. **`event` backend abstraction** → pluggable consumer interface, backend-agnostic grammar via `event_sources:`, at-least-once + inbound dedupe, one blessed reference backend in M3 (5.11).
8. **`respond: sync` semantics** → compile-time interrupt-free requirement + mandatory timeout with async upgrade (202 + execution id) (5.11).
9. **Store backend binding** → alias-only: stores name abstract slots; per-target deploy files define them; no inline provider config, no address-keyed overrides (5.8).
10. **LLM providers & models** → `provider.*` (connection) / `model.*` (behavior) split; schema-validated provider settings; ordered failover routes on infrastructure conditions only; no inline overrides on agents; env-ref-only secrets surviving unresolved into the IR (5.9).
11. **Codegen target** → LangGraph TypeScript first; a Python backend is a possible v2 target (§4, 5.12).
12. **Compiler implementation** → Rust single-binary CLI (parse/resolve/validate/codegen); CEL via the Rust `cel` crate at validate time and a JS evaluator at runtime, kept in lockstep by a shared conformance corpus (5.5, 5.12).
13. **`agent_access` on store attachment** → accepted: a `stores:` entry may narrow the synthesized tool surface to read-only (`agent_access: read`; default `read_write`). One enum buys declarative least-privilege for store tools, the same posture placement isolation takes for compute (5.8, 5.10; grammar D37).
14. **`max_tool_iterations` on agents** → accepted, default 8: the intra-agent tool loop was the one remaining unbounded loop in a compiled graph; a declarative bound completes the static-termination story that 5.4 starts (5.4, 5.5; grammar D51).
15. **Env-ref presence checking** → launch-time, not build-time. 5.8/5.9 originally said `build` checks presence while the M1 milestone said process start; the artifact-portability posture decides it — a build must succeed anywhere, including CI holding no secrets, or committable IRs and least-privilege distribution (5.10) break. Generated code verifies its environment at process start; `run`/`serve` fail fast before invoking the graph. `validate` and `build` check syntax only (5.8, 5.9).
16. **The schema a provider is handed** → the compiler's JSON-Schema lowering, on the wire, not a `withStructuredOutput` conversion of the emitted Zod. The load-bearing property is constrain==parse equality: the schema a model is constrained by must be the schema its answer is parsed with, or an agent can honor its contract and still fail the parse. The pinned `@langchain/core` Zod conversion silently drops refinement-spelled constraints (`format:`, `uniqueItems`, length bounds), breaking that equality; the two columns are equal by construction only for the JSON lowering, proven document-by-document in CI. A permanent gate measures the dropped-constraint behavior so the choice is revisited if the conversion ever stops lossy-dropping (5.2; codegen schema module).
17. **Fan-out and subgraph shaping** → map instances run inside the map node's own LangGraph task (bounded admission, index-tagged joins) rather than via top-level `Send`, and `flow:` nodes invoke separately compiled graphs rather than in-graph subgraphs. Rationale: instance isolation (item-scoped context, per-instance history, §9.4 instance paths) and the grammar's per-node §7.6 semantics are guaranteed directly instead of recovered from scheduler internals; grammar 7.6.4 clause 1 was verified to hold under this shaping. The 5.5/5.6 codegen columns are updated; `Send`/subgraph remain available shapings if LangGraph's semantics ever make them cheaper to prove (codegen ledger).
18. **Runtime and package manager for generated artifacts** → **Bun by default; Node >= 22.18 a supported fallback; generated code free of Bun-only APIs.** Owner decision ("default to bun runtimes and pkg manager for generated artifacts"), interpreted as a statement about the *surfaces around* an emitted project rather than about the code inside it. Bun is what the emitted `README.md` documents first, what the generated-code gates, the property harness and the acceptance suite execute compiled graphs with, and what `run`/`serve` will launch; the gates install from a committed `bun.lock` with `--frozen-lockfile`, and CI pins the Bun version exactly for the reason 5.12 pins LangGraph exactly — a runtime that moved underneath CI would change what a green suite means with no commit saying so. The fallback is not a courtesy: `engines.node` carries the floor, `@types/node` stays on the same major, one gate installs a golden with npm and type-checks, constructs and runs it under Node (including re-deriving the inherited-property refusal list, which is the JavaScript *engine's* and must hold on both), a second answers both shared conformance corpora under that engine (a `format:` is a `RegExp` and the emitted CEL evaluator is `BigInt` arithmetic, so a corpus run under one engine says nothing about a reader on the other), and a static gate refuses any emitted module that names a `Bun` global, a `bun:` specifier, or an import outside the pinned set. The manifest itself stays installer-neutral: no `packageManager` field — it is corepack's, corepack does not manage Bun, and emitting it would pin every generated project to one Bun release while buying no determinism the exact version pins do not already give — and no emitted lockfile, because the reader's lockfile is the reader's (5.12).

19. **Instance identity for model-invoked subflows** → a per-call ordinal, fixed by the grammar. A flow-tool invocation contributes the frame `<tool_name>/<call_ordinal>` beneath the invoking agent node's own frame, where the ordinal counts prior invocations of that flow-tool within this agent-node execution. Distinct calls in one tool loop get distinct instance paths (the collision §9.4 exists to prevent), and an agent-node retry restarts the ordinals, so the Nth call of a retried attempt reuses the Nth key of the failed one. Because the emitter is a nondeterministic model, that reuse is **positional, not semantic** — the accepted at-least-once compromise, stated openly in the grammar. The alternatives lose outright: a provider tool-use id is fresh on every retry, so key-reuse dies and every agent retry re-fires every child flow's side effects; an argument hash merges two intentional identical calls. Like every other frame, the key is derived, never authored — no spec construct configures it and there is nothing for `validate` to check (grammar §9.4).

20. **Trace join for model-invoked subflows** → both surfaces, split by role — the span-link pattern. The child instance's full trace attaches as a canonical **dispatch record** keyed by its instance path (q19), exactly as a `flow:` node's instance does; the tool-call entry inside the agent's `ModelCall` records the call, the result the model saw, and the child's instance path as a **link**. Both invariants survive: every subflow instance in a trace is findable as a dispatch record (one shape for `plan`, replay, and the M2 tracing conventions to walk), and the tool loop's story is complete inside the `ModelCall` at the cost of one indirection. Nesting the child under the `ModelCall` alone would break the first invariant; a bare dispatch record alone would leave a tool call whose result came from nowhere.

21. **Answering a `human` pause from `run`** → accepted, and it closes a gap the human-node runtime (resolved q4) left open: a flow with a `human` node in it and no `http` trigger on it was **un-completable**. `run` reached the pause, wrote the trace with `status: "interrupted"` and exited `3` pointing at `serve`'s resume route — and a wait lives in the serving *process*, so the route that answers it belongs to a process `run` never started. Owner decision: **when a `run` parks at a pause and standard input is a terminal, the emitted CLI renders the node's `input:` — what the human is shown — reads the answer there, validates it against the declared `output:` exactly as the resume route does (an answer that does not fit re-prompts and does *not* consume the wait), and the execution carries on in the same process.** `timeout:`/`on_timeout:` budgets keep running while it waits, so an expiry routes exactly as it would under `serve` and the withdrawn prompt says so. A run whose standard input is **not** a terminal keeps the exit-`3` behaviour, so nothing hangs headless. Mechanically it is **the same wait board with a second delivery surface** — parallel to the way grammar §9.4 fixes one idempotency-key delivery surface per binding kind: which pause an answer addresses, what schema it is held to and what each refusal means are decided once, for both surfaces, so the two cannot disagree about one board. Four details are the terminal's own and are stated where a reader meets them (grammar §8.7, the emitted `README.md`). The framing is **one JSON value per line**, because a value spanning lines has no terminator a prompt could recognize without either guessing or hanging on a malformed one. The pauses of one execution are asked **one at a time**, each question being the **lowest-id pause open when it is asked** — the order the status route publishes them in, so a set of pauses waiting together is asked in the order the composition fixes rather than the one the scheduler parked them in. It is that rather than a total order over the run's pauses because a question already on the screen is not taken back: a pause that opens while one is being asked is asked after it, whatever its id sorts as. `AGENT_COMPOSE_INTERACTIVE` (`1` / `0`) decides the surface where a terminal cannot: it is how a **script** answers a pause, and how a supervisor keeps a run on the exit-`3` path it reads; a value that is neither is a usage error, not a setting nobody read (grammar D50). And standard input **ending** withdraws the surface — every pause still waiting, and every one the run opens after it, becomes the same interrupt a run with no surface raises — so a script that answered too few questions ends where it stood instead of parking for ever. Durability is unchanged: this is still one process and one parked promise, and making a wait survive a restart is durable execution's job (M3) (5.5, 5.11).

22. **What a tool call the contract refuses does** → **it returns to the model as a tool_result error so the model can self-correct**, rather than failing the agent node the way the flow-as-tool runtime (resolved q19, q20) originally shipped it. Owner ratification, and the scope is exactly two events wide. **Bounces**: arguments the tool's declared schema refuses — uniformly on all three surfaces a tool can be attached from, a `tool.*`'s `input:`, a synthesized store tool's argument row, and a `flow.*`'s `inputs:` — and a call naming a tool the agent was not offered. **Still fails the node**: failures of the tool's *execution* — an `exec:` exiting outside its accepted list, an `http:` request refused, a child flow instance that failed, a store backend that could not answer — where `retry:`/`on_error:` keep governing exactly as before. The line is what the model could do about it: a schema refusal is a statement about the *call*, which the model chose and can choose differently, while an execution failure is a statement about the world, and handing that back would ask a model to route around a broken system — the decision 5.3 takes away from models. The rule this replaces made a composition's reliability depend on a model never mis-typing an argument, and pushed authors toward loosening schemas until nothing was checked, which costs the constrain == parse property §9.16 is built on. **Termination is unchanged and is what makes the bounce affordable**: a correction is another model call, so a bounce spends one of `max_tool_iterations` (§9.14) — no second counter — several refusals in one answer are corrected together for one iteration, and a model that never corrects spends the bound and fails the node, with the node's error naming the last refusal it was holding so the run is diagnosable — *holding* read strictly, so a loop whose last call worked names none and the message never reports a mistake the model already corrected. Three consequences are stated where a reader meets them (grammar §5.4, §6, §11.5, D119): every call of an answer comes back to the model, refused or not — under the call's own id on both provider wire shapes, which refuse a request that leaves one unanswered, except for the one call Chat Completions will not let a request name at all (a tool the agent was never offered), whose `tool_call` is dropped from the replayed turn and whose refusal travels there as a `user` turn instead; a refused call spends **no** call ordinal — §9.19's ordinal counts a flow-tool's *invocations* and a refusal reaches no flow — so instance paths do not move when a model makes a mistake before them, and a node `retry:` whose second attempt needs no correction re-derives the first attempt's keys instead of re-firing every child flow's effects; and the refusal names what a compiler diagnostic would name — the tool as the *wire* offered it (a `tool.*`'s local name, the only spelling a corrected call could use), the field, the constraint, an excerpt of the offending value (G3) — which is one sentence written for the model that must act on it and for the person reading `ToolCallRecord.error`. The same tool reached from a `function:` node keeps naming its address and keeps failing the node: nothing there proposed a call, so there is nobody to hand it to (grammar §6, §8.4). The trace records it as a new `outcome` member, `"refused"`, rather than reusing `"failed"`, which bumped `trace_version` to `4`: version `3` defines `"failed"` as a call that ended the node and whose answer the model never saw, and both halves are false of a refusal (`docs/trace.md` §10.3.3) (5.1, 5.2, 5.3, 5.5, 5.8).

23. **The shape of the discovery surface, and of the skill** → **five verbs, three of them bound to a registry the compiler already keeps.** §7 M2's exit criterion is that a user downloads a released binary, hands their coding agent the skill, and builds and runs flows locally with no clone of this repo — so every byte an agent needs is embedded in the binary (5.12) and nothing is looked up at runtime. `docs [<topic>]` prints a topic index or one topic document; `explain <code>` prints an expanded explanation of one diagnostic code; `schema` prints the published JSON Schema byte-identically; `init [<dir>]` scaffolds a project that validates clean; `skill` prints or installs the skill. **The topics are curated derivatives, not slices**, and that is the load-bearing choice: `docs/grammar.md` is normative and is written to be *complete*, which is the wrong shape for a reader with a context window — so each topic is example-led, one screen of runnable YAML before any rule, and closes by naming the grammar sections it derives from. A derivative can drift from its source silently, so **three binds hold it**: every topic file is registered and every registered topic has a file; every numbered heading of `docs/grammar.md` is claimed by at least one topic's `Normative source` line, and every claim names a heading that exists, so a new grammar subsection fails a test that names it until somebody decides which topic teaches it; and the `cli` topic names every verb the binary has and every environment variable it reads. That last bind runs **both ways round**: documents ⊇ registry catches a verb nobody documented, and registry ⊇ documents catches the opposite and more damaging failure — a document instructing a reader to run something this compiler does not have — so every `agent-compose <verb>` and `agent-compose docs <topic>` written in code voice anywhere in the embedded documents must name a verb clap has and a topic the curriculum has — and, since a real verb missing a required argument is the same usage error by a likelier route, must also name at least as many arguments as clap's own usage line for that verb requires, everywhere a reader is being told what to type. The exception is a **table cell**, where these documents name a verb as a noun ("the terminal of an `agent-compose run`"): there the invocation is the row's subject rather than a line to run, and the alternative — arguments everywhere — would force those sentences into worse prose. The carve is a structural proxy with a named hole (an instructing invocation written inside a table), bounded by a table cell being a poor place to put a command anybody should type; naming a verb that does not exist is refused in a table cell as anywhere else. The alternative — generating topics from the grammar — was refused for the reason the derivative exists: a generated topic is the grammar again, at the grammar's size. **`explain` binds to the diagnostic registry by an exhaustive `match` over `DiagnosticCode`**, so a new failure class does not compile until it has an explanation; the reverse direction (no orphan explanation) is a test. Each explanation says what the check protects, shows a minimal spec that triggers it — and the spec is *run*, so an explanation whose example stopped triggering its code is a test failure rather than a lie shipped in a binary — then the fix and the cross-reference — which is itself bound, by the same parser that reads a topic's `Normative source` line: every grammar section and every decision an explanation cites must be one `docs/grammar.md` has, so a renumbered subsection or a retired decision cannot leave dozens of embedded documents pointing at nothing. *Coverage* stays the topics' obligation alone; what an explanation owes is a pointer that resolves. **Every published example is run**, marked by its fence's info string: a topic's opening spec must validate clean, and a deploy file (```` ```yaml deploy <target> ````, the one document kind `validate` cannot be pointed at alone) is written beside its topic's own composition and resolved under that target. An explanation may also write its **repair** out as a whole spec, held to the clean verdict a topic's example is: the fix bullets are the one part of an explanation nothing runs, and a repair that clears the rule it is about and lands the reader on a *second* diagnostic is worse than no repair — they followed the instruction they were given, inside a binary they cannot correct. Every explanation whose fix has a neighbouring check to fail carries one, and which those are is another set equality rather than a floor. Which documents *lack* an example is held to **set equality** against a named list with a reason each, not to a count: a count is satisfied by the documents that kept theirs while the ones that lost theirs go unchecked. **Every human report that carried a code** gains one trailing line pointing at `explain`, once per run rather than once per diagnostic: `validate`'s; the ones `build`, `run` and `serve` print before refusing, since those three validate first and print the same block through the same renderer; and a `plan`'s, which carries codes by two routes of its own — a `validation` section listing the findings the two sides disagree about, and, for a spec that does not resolve, the same diagnostic block `validate` would print. A reader who met a code without having typed `validate` is *further* from the verb that would explain it, not closer, which is where the pointer is worth most, and a `plan` is the report where that reader is likeliest of all — they were reviewing a change, not validating a spec. The JSON reports are untouched, because a machine reader gets the code and does not need to be told a verb exists. **The skill teaches the loop, never the grammar.** It is one self-contained document about `init` → edit → `validate` → `explain` → `docs <topic>` → `plan` → `build`/`run`/`serve`, with a verb table and the pointer that the topics are the curriculum; restating a grammar rule inside it would put a copy of a normative sentence in the one artifact this project cannot re-publish, since it is installed into somebody else's agent. Drift tests hold it to naming every verb and to listing the curriculum in the curriculum's own order — the two **registries the binary owns**, which are exactly what it may safely restate, as against a grammar rule, which it may not. **The install is one write under two roots.** `--agent claude` writes `.claude/skills/agent-compose/SKILL.md` and `--agent codex` writes `.codex/skills/agent-compose/SKILL.md` — the same path shape under each agent's own skills directory, project-local or under `$HOME` with `--global` — because both agents auto-detect the **same portable `SKILL.md`**: YAML frontmatter, then the document. So there is one installed document and one code path, parameterized by the root directory alone, and an agent that adopts the convention is a row in a table rather than a posture of its own. Each root is a directory whose whole content is skills, so either install refuses to overwrite a file that differs and no-ops on one that matches — differing by **bytes**, so a file that is not text at all is the refusal's case (exit `1`, the answer is no) rather than an unreadable one (exit `2`, the command could not run): what the refusal protects is that path's contents, and "could not decode" is not an answer to whether those contents are ours. *Owner correction (2026-08-20): this entry first recorded an asymmetric pair, `--agent codex` **printing** the document under a header on the reading that Codex's only surface was the user-authored `AGENTS.md`, which this compiler does not edit. Codex has first-class skills in the portable format, so that reading made the codex arm a worse install for no reason; the two arms are symmetric, and the print-only posture is gone.* (§7 M2, G3, 5.12).

24. **The shape of the release pipeline** → **four static artifacts, a hand-rolled workflow, and a dry run of it on every pull request.** §7 M2's exit criterion opens with "a user downloads a released binary", so the deliverable is the download: `agent-compose-<version>-<target>.tar.gz` for `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl`, `x86_64-apple-darwin` and `aarch64-apple-darwin` — each holding the one binary, and the repository's `LICENSE` when there is one to hold — plus a single `SHA256SUMS` over all four, attached to a published (never draft) GitHub release with generated notes. **musl rather than glibc**, because 5.12's single binary is a claim about *where it runs*: a glibc build carries the build machine's symbol versions, so it fails on an older distribution and on alpine outright, while a static musl build survives both — and the build job asserts static linkage (`file` reporting `statically linked` or `static-pie linked`) rather than trusting the target's name. **Hand-rolled GitHub Actions rather than `cargo-dist`**: the product is one binary with no runtime dependencies, so packaging is a `tar` and a `sha256sum`, and owning ~200 lines of YAML outright beats pinning a generator whose version churn would dwarf the surface it generates. Revisit if the target list multiplies, or if an artifact stops being one file — installers, code signing and notarization, package-manager taps are where a generator starts earning its pin. **The tag and the crate version are one number.** A guard job reads `cargo metadata` and refuses to build when the tag and the crate version disagree, naming both; and because an artifact named for a version the binary does not report is the failure a user cannot diagnose, each smoke test holds `--version` to the version its archive is named for *and* to its own target triple. That line is new and carries three facts — crate version, short commit, target — since a binary that was downloaded rather than built has no other way to say which build it is; `GIT_SHA` wins over the checkout so a release names the sha it was cut from, and a tree with no `.git` beside it says `unknown` rather than failing to build. **The acceptance test is the dry run.** Build, check and package are a **callable** workflow, and both paths call it — the tag path with a tag to guard against, the pull-request path with neither a tag nor a publish step — so the two cannot drift into agreeing only until one is edited. **The pull-request gate builds the two Linux legs; the two macOS legs run on a tag and on a manual `workflow_dispatch` of the dry run.** This repository is private, where a macOS runner minute bills at ten times a Linux one, and two Darwin legs on every push of every pull request is a standing charge against a rare failure: the crate is pure Rust with no platform-specific code, so what a macOS leg catches that a Linux one does not is a linkage or a toolchain difference rather than a compile error. The rehearsal trigger is the compensation — `workflow_dispatch` runs the same workflow over all four legs from any branch, so a release can be practised in full without a tag being pushed for it — and the dry run cancels superseded runs of its own ref rather than paying for answers about commits that have already been replaced. The pull-request path additionally runs `install.sh` end to end against the artifacts it just built, in a local-artifact mode the script documents, including both refusals a checksum can produce. What the gate does **not** cover, stated rather than assumed: `gh release create` itself, which only a tag runs; **a macOS-only break**, which now surfaces at the manual rehearsal or at the tag rather than on the pull request that caused it — the honest price of the paragraph above; **the tag guard's refusal branch**, since a pull request passes no `expected-version` and so exercises the guard reading `cargo metadata` but never its disagreement; and — on the one leg where an arm64 macOS runner turns out to have no Rosetta — the *execution* of the x86_64 macOS binary, which then keeps its architecture and linkage assertions, loses its smoke test, and says so in a warning rather than passing quietly. **An unverified download is never installed.** `install.sh` (POSIX sh, `curl` or `wget`, `sha256sum` or `shasum`) resolves a release, downloads the archive and the `SHA256SUMS`, matches the archive's name as a whole field in it, and hard-fails both when the checksum disagrees and when the file says nothing about the archive — leaving the install directory empty either way. **The documented install is two commands rather than a pipe**: fetch the script, then run it. A pipe discards `curl`'s exit status, so a URL that answers `404` — which is what a private repository and an unreleased one both answer — pipes an empty body into a shell that runs it and exits `0`, installing no compiler and reporting no failure; the two-command form fails where the failure is, and leaves the script on disk to be read before it is run. The binary is **staged inside the install directory and renamed into place**, because a temporary directory is routinely another filesystem (`/tmp` is a tmpfs on most Linux distributions) where `mv` degrades to a copy over the destination — not atomic, and a truncating write onto a binary that may be executing. Until the repository is public and has a release, the README says plainly that those URLs `404` and names the two routes that work meanwhile: building from source, and the dry run's uploaded artifacts. Two mechanical choices are worth recording because each removed a dependency rather than adding one: aarch64 Linux links with **`rust-lld` out of the toolchain** — every dependency of this workspace is pure Rust, so no cross C toolchain, container or third-party build action is involved — and **`qemu-user-static` runs the resulting static binary directly**, with no container and no `binfmt` registration, so the one leg an x86_64 runner cannot execute natively is smoke-tested rather than merely inspected. Two actions outside the `actions/*` namespace are used, both already in `ci.yml`: `dtolnay/rust-toolchain`, which installs the *pinned* toolchain with an added target (the alternative is hand-written `rustup` lines that would drift from CI's), and `Swatinem/rust-cache`, which the pull-request gate turns on for speed and the release path leaves off — nothing a previous run left behind can reach a binary somebody downloads. **Both are pinned by full commit sha rather than by `@stable` or `@v2`**, in the release workflow and in `ci.yml` alike, since one supply-chain posture repo-wide is easier to hold than two: a branch and a tag are both whatever their owner moved them to last, and on the path that produces bytes other people download that is somebody else's push landing inside our release. The toolchain the action installs is named in the workflow rather than by the branch the action came from, so what the pin holds still is the action's own code and nothing else; bumping either sha is a commit that says so, in both workflows together. **The posture is repo-wide rather than release-only**, so the third action outside that namespace — `oven-sh/setup-bun`, which only `ci.yml` runs, since nothing a release builds needs a JavaScript runtime — is pinned by sha on the same terms: `@v2` is a tag its owner moves, and a rule with one exception left in it is not a rule. *Owner correction (2026-08-28): the tag-equality guard is inverted — **the tag names the version, and the release stamps it into the build**. The equality rule made every release a two-step ceremony: a version-bump commit, then the tag — and a delete-and-retag whenever they drifted, which is how the first `v0.2.0` push was refused — while each bump also churned every golden fixture, because generated projects write the crate version into their file headers. Now the `version` job holds a tag only to being shaped like a release (`vMAJOR.MINOR.PATCH`), each build leg patches `[workspace.package]` and `Cargo.lock` to the tag's number before its `--locked` build, and the committed crate version is a development placeholder the dry run builds under. What the equality guard protected still holds and is still checked, one step later: the smoke test refuses any binary whose `--version` is not the number its archive is named for, so a release still names one build — by construction rather than by refusal. The dry-run gap moves with the mechanism: what a pull request cannot exercise is now the stamp step rather than the equality refusal.* *Owner direction (2026-08-28), the second half of the same correction: **a merge to `main` releases itself when its commits earn it.** Squash merges use the PR title as the commit subject and PR titles are held to Conventional Commits (this document's own Git conventions), so `main`'s first-parent history is a machine-readable bump ledger: `feat:` earns a minor, `fix:`/`perf:` a patch, a breaking change (`!` subject marker or a `BREAKING CHANGE:` footer) a major — read as a minor while the major is `0`, the pre-1.0 convention — and docs/chore/ci/test/refactor/build earn no release alone, riding with the next one. The decision reads first-parent subjects only (a squash body lists the branch's inner commits, and an inner `feat:` bullet is not a released feature) plus the footer, which is defined to live in the body. When a bump is due, `auto-release.yml` calls the same `release-artifacts.yml` as every other path and publishes with generated notes, creating the tag as it does — and a tag created by the workflow token fires no workflows, so the tag path does not run a second copy. The tag path survives as the manual override: skip a number, or re-cut a release whose run failed. Racing merges are serialized rather than cancelled, so the second run counts from the first run's tag; a computed number whose tag already exists stops the run and names the stale tag, rather than guessing. Changelogs are the generated release notes and nothing more — a `CHANGELOG.md` maintained by CI is a bot pushing to `main`, which this pipeline deliberately never does; the release notes carry the same conventional subjects the ledger is made of.* (§7 M2, 5.12).

25. **What an `anthropic` or `openai` provider that holds no key means** → **`api_key` is required when the provider points at the vendor's own endpoint and optional when `base_url:` names something else**, and an absent key means the compiled runtime sends **no auth header at all** rather than an empty one. Owner ratification, and the case is corporate: a gateway injects the vendor credential server-side and employees never hold a key, so `kind: anthropic` with a `base_url:` and nothing else is the shape those deployments write — and 5.9's "swapping a project from hosted to local inference is a one-line provider edit" was untrue for the two kinds whose row made the key unconditional, which is what forced `openai_compatible` and a re-pointed model on a deployment that is still talking to Claude. The rule is one sentence with a reason on both halves: **pointing at the vendor's endpoint needs a key** — nothing else authenticates there, and the runtime's default `https://api.anthropic.com` is what an omitted `base_url:` resolves to — while **a gateway that injects one is named by `base_url:`**, which is the only thing in the definition that can say the traffic is not going to the vendor. A gateway that wants its *own* token still has `headers:`, which is interpolable, so `${PROXY_TOKEN}` reaches the wire without pretending to be a vendor credential. **The rejected alternative is simple-optional**: making `api_key` merely optional on both kinds admits `kind: anthropic` alone, which builds, ships, and then 401s on its first live call — moving a forgotten key from `validate` to production, in exchange for one fewer rule. G3 makes error UX a product feature and the whole point of the static pass is that a composition that cannot work does not compile, so the conditional keeps the forgotten-key failure where it was and buys the gateway shape with a diagnostic that names both repairs. `azure_openai`, `bedrock` and `vertex` are untouched — Azure has no default endpoint to reach and no keyless posture to describe, and the two SDK-reached kinds authenticate through their cloud's own credential chain — and `openai_compatible` was already the fully flexible kind. The compiler reports it as `missing-credential`, the published schema enforces the same conditional per Appendix B, and `docs/grammar.md` §12.1 and Decision D120 state it where an author meets it (5.9, G3).

26. **What mechanism makes an execution durable?** → **A journal + replay of the record this runtime already keeps**, not a LangGraph checkpointer. Owner ratification (2026-08-22). The checkpointer route — the milestone's original "Postgres checkpointer wiring" spelling — was written before resolved q17 shaped subflow and map instances *inside* a task and resolved q4 parked `human` waits on an in-process wait board; both put the majority of a mid-run execution's live state where a graph-level checkpointer never looks, so adopting one now would mean restructuring both features to be checkpointer-visible, in exchange for coupling the durability story to LangGraph's persistence API and its version churn. The journal route fits the architecture as built: every effect carries an idempotency key (resolved q10), store reads are recorded so "a replay has something to consume" (`docs/trace.md` §6, normative since trace v1), every model call's attempts are recorded, and traversal ordinals are deterministic — the trace format was designed as a replay log, and durability is making the runtime *write it as one and read it back*. What this resolution changes is the standing of that discipline: `docs/trace.md`'s replay language stops being documentation and becomes the tested recovery contract (5.11, 5.12).

27. **Where does the journal live, and how is that chosen?** → **A deploy-target slot, exactly as `storage_backends` are** — the composition says nothing, the target binds it. Owner ratification (2026-08-22). `--target local` binds a SQLite journal file beside the project (durable by default, zero configuration, one file to delete), a distributed target binds Postgres, and both sit behind one journal interface so the runtime cannot tell which it got. The rejected alternative is a grammar-level knob (`durability: on|off` in the spec), which would make the same composition durable on one machine and not another *by author declaration* — placement facts belong in deploy files (5.10), and whether an execution survives a restart is a placement fact (5.10, 5.12).

28. **What does v1 durability scope cover?** → **Three clauses, and two named exclusions.** Owner ratification (2026-08-22). **`serve` auto-recovers**: on process start it replays every execution the journal holds open, including executions parked on `human` waits, which re-park with their wait ids intact — the wait id is deterministic (node path + ordinal, resolved q4/q20), so a resume request arriving after the restart still finds its wait. **`run` journals but does not auto-resume**: a crashed one-shot run is resumed explicitly by a new verb (`agent-compose resume <execution>`), because a CLI invocation ending is not evidence the user wants it re-run. **Triggers fire once**: recovery replays executions that exist; it does not re-fire the trigger that created them. Out of v1 scope, stated: cross-process migration (a journal written by one host resumed on another is M3-distribution's problem) and journal compaction (5.11).

29. **What does replay execute, and what does it not?** → **Replay is read-only up to the frontier.** Owner ratification (2026-08-22). A replayed execution consumes recorded model answers, recorded store reads, and recorded tool results by idempotency key — byte-for-byte, no re-issue — and only the frontier (the first effect the journal does not hold) reaches the network. The stated consequence: determinism of everything *between* effects (routing, CEL evaluation, ordinal assignment) becomes a durability-correctness requirement rather than a trace-niceness, so the CEL conformance corpus and the ordinal rules join the recovery contract; and a divergence discovered at replay time — a recorded answer that fails the current contract — fails the resume with a diagnostic naming the divergent step, rather than silently re-executing an effect the journal claimed to hold (G3, 5.12).

30. **How does a composition reach a tool the *provider* runs?** → **A provider declares `server_tools:` — an array of config objects in that provider's own wire vocabulary, appended verbatim to the `tools` of every request that connection serves — and the compiler checks it in two tiers.** Owner ratification (2026-08-22). The runtime **dispatches nothing** for them: a server tool executes on the provider's side, inside the model call, and its results arrive woven into the assistant's turn, so a `server_tool_use` block is not a tool call the agent's loop answers and replay is untouched — the use happened inside the recorded model call (5.11, resolved q29, `docs/durability.md` §3.1). That is also why the entry is a **wire object** rather than a construct of this grammar: nothing in the composition dispatches it, so nothing in the composition has to be able to spell it. **The two tiers are how G3 coexists with the governing constraint, which is *no manual support treadmill*.** A server tool the vendor ships tomorrow must be usable the day it ships, without waiting for a compiler release. So the compiler keeps a **curated table** of the tools each `kind` is known to serve and checks an entry naming one *strictly* — a modelled field given the wrong kind of value, a value outside a stated range or closed set, a required field left out, two fields the vendor refuses together are all errors, with a diagnostic naming the repair — while anything the table cannot speak for is a **warning that says exactly what could not be verified** and travels to the wire unchanged (`unknown-server-tool` for a `type:`, `unknown-server-tool-field` for a key inside a `type:` the table does model, because vendors add parameters to tools they already ship). The two rejected alternatives are the two ends of that axis: a table that **gated** *is* the treadmill, and **no table at all** makes a misspelled `max_uses` a 400 on the first live call with no span. **A suite belongs to a connection, not to an agent**, which settles three things at once: every agent whose model resolves to that provider holds it and scoping one to a single agent means defining a second provider (providers are cheap); a route's failover capability is per-chain-member by construction, so `validate` **warns** (`mismatched-server-tools`) rather than refusing when members declare differing suites, since which tools were on offer depends on which member answered and a fallback vendor with no web search is still a fallback; and the suite lands in the same `tools` array the agent's own tools land in, which makes 5.5's one-name-one-tool rule an **error** on two more pairs (two entries of one suite that reach the wire under one name, and a server tool whose name an attached `tool.*`/`flow.*` or a synthesized store tool already takes). **Launch scope is `anthropic` and `openai`, plus `openai_compatible` wholly second-tier**; `azure_openai`, `bedrock` and `vertex` refuse the key outright rather than dropping it silently, naming that scope. **Declaring a suite can move the connection's wire**, and this is the one place the decision reaches beyond the key: OpenAI's built-in suite is the **Responses** API's and Chat Completions does not carry it, so an `openai` provider that declares `server_tools:` speaks Responses for **all** of its calls and one that declares none keeps Chat Completions untouched — one provider, one wire, because a connection that switched per request would make "what did this model see" depend on which agent asked. Moving the wire moves what that wire has: two of §5.9's `settings:` keys are Chat Completions' alone (`stop:`, `seed:`) and become a compile error on the models that connection serves rather than a 400 on the first call, two change spelling and the runtime translates them (`max_tokens` → `max_output_tokens`, `reasoning_effort` → `reasoning: { effort }`), and the service-side default for `store` differs, which the models topic states where an author meets the seam. `anthropic` rides the Messages wire it already speaks, and `openai_compatible` rides its Chat Completions `tools` array with every entry unverified — no table could be authoritative about what a gateway honours. Stated in `docs/grammar.md` §12.1 and Decision D122, where an author meets it (5.9, 5.5, G3).

31. **What runtime built-in tools (bash, file I/O) are, and what bounds them** → **four curated tools, opted into per agent node one name at a time, bounded by a mandatory root and a timeout.** Owner ratification (2026-08-22), following the owner's scope call that both built-in tool kinds are wanted and opt-in. An author could already hand-roll a shell through a `tool.*`'s `exec:`; the curated set removes the boilerplate without moving the trust boundary — a model holding bash is arbitrary code execution on the host running the graph, which is why every bound here is explicit. **The set is `builtin.bash`, `builtin.read_file`, `builtin.write_file`, `builtin.list`** (list = directory listing/glob), growable later by resolution rather than by drift. **Opt-in is per agent node, one tool name at a time** in the node's `tools:` list — never ambient, and never a single switch that grants the set, because "which capabilities does this agent hold" must be readable off the node that holds them. **File tools take a mandatory `root:`** and refuse any path that resolves outside it (resolution, not string prefix — symlinks and `..` count); **bash runs with that root as its working directory and a timeout**, resolved from `PATH` at runtime, and a host with no `bash` fails the call as an execution failure with an error naming the requirement — Windows posture deferred until someone runs graphs there. Refusals and failures follow the standing rules: a call the schema refuses bounces per resolved q22; an execution failure (nonzero exit, timeout, root escape, missing shell) fails the node under `retry:`/`on_error:` like every `exec:` tool. **v1 containment is root + timeout only** — the tools run with the runtime's own privileges, exactly as a hand-rolled `exec:` tool does today; containers/seccomp and any deploy-target-level restriction (refusing bash on a distributed placement is a placement fact) are deferred to the distribution work, stated rather than implied. **Traces are unchanged**: builtin outputs are recorded in the trace exactly as any tool result is under the existing `ToolCallRecord` rules and `docs/trace.md` §11 — no new trace surface — while the journal (resolved q26–q29) holds full outputs as private recovery data, which is the journal's already-stated posture (5.5, 5.12, G3).

32. **What authenticates an inbound `http` trigger call, and which routes does it cover?** → **A per-trigger `auth:` block, two kinds in v1 — `bearer` and `hmac` — and an execution's resume and status routes enforce the auth of the trigger that started it.** Owner ratification (2026-08-28). v0's posture was "deploy behind your own gateway" (5.11); webhook-style events make the generated app the thing a vendor calls directly, so it must verify callers itself. **`bearer`** compares a static secret against a named header (default `Authorization` with a `Bearer ` prefix) in constant time, the value arriving by `${ENV}` interpolation exactly as provider `headers:` do — a secret never lives in the spec text (5.8). **`hmac`** verifies a signature over the raw request body — configurable `header:`, `algorithm:` (`sha256`/`sha1`/`sha512`), `encoding:` (`hex`/`base64`) and `prefix:` (e.g. `sha256=`) — which is the GitHub-shaped family most webhook vendors speak. Schemes whose signed payload is more than the body (Stripe's timestamped `t.body` with a tolerance window) are deferred: each is a vendor-specific shape, and genericizing them now is the support treadmill resolved q30 refused — vendor presets can grow later as a curated table on q30's own terms. **Auth is declared per trigger, never server-wide**, for the reason builtins are per node (resolved q31): who may invoke this flow must be readable off the trigger that exposes it. **Coverage is the subtle clause**: the resume and status routes are per-execution, and resume *injects data into a parked run* — strictly more sensitive than start — so both enforce the auth of the trigger that started the execution; an execution a no-auth trigger started keeps open routes, and one an authenticated trigger started never answers an unauthenticated poll. `run` is untouched — no server, no caller to verify (5.11, G3).

33. **How does a callback receiver verify the caller, and what bounds where callbacks may point?** → **Opt-in outbound auth on the trigger — `hmac` signing and/or a static `bearer` header — and declaring either makes `callback_allow:` mandatory; a trigger with no outbound auth is a test posture that may POST anywhere, and the docs say so.** Owner ratification (2026-08-28), both clauses owner-shaped: outbound **`bearer`** mirrors inbound q32 because some receivers verify a static token more readily than a signature, and the allowlist is required *exactly when auth is configured* — a deployment careful enough to authenticate its callbacks must not deliver them wherever a payload said, while one that configured nothing has declared itself a test environment and gets no ceremony. **`hmac`** signs the callback body with HMAC-SHA256 and sends signature, delivery-id and timestamp headers — deliberately symmetric with inbound q32, so one verification recipe serves both directions. **`callback_allow:`** is a list of URL patterns on the trigger; the callback URL comes from the trigger payload (D110) and is attacker-controlled by construction, so a URL outside the list is refused when it is read — at parking or settle, not at start — and recorded as a refused delivery rather than anybody's failure. `http` URLs stay legal — localhost development is the common first case. Private-IP and DNS-rebinding hardening is named out of v1 scope rather than half-shipped: SSRF-hardened egress is the gateway's job in the deployments that need one (5.11, resolved q32).

34. **When does `callback:` fire, and what does it carry?** → **On lifecycle events — every quiescence that opened new pauses, and settle — one webhook per event, each carrying the status route's report plus delivery metadata naming the event.** Owner ratification (2026-08-28): subscribed systems receive the run's *lifecycle*, not only its end. A parking fires **one** webhook listing every pause then open — never one per pause, because a `map` over a flow with `human` nodes would spray a receiver with N deliveries about one quiescence — and the body is the same report the status route serves (resolved q4: what the human is shown, the answer schema, the resume URL, per pause), so a receiver builds its UI from a push exactly as it would from a poll and the two surfaces cannot disagree. Delivery metadata names the event kind and its ordinal, so a receiver routes on kind and orders on ordinal. **No subscription filter in v1**: a receiver ignores kinds it doesn't want, and a filter surface is addable later without breaking anyone, so it waits for demand. Resolved q29 stands untouched: a replay divergence fires nothing, and the settle delivery stays gated on the execution actually being closed (5.5, 5.11, resolved q29).

35. **What does durable delivery mean for a callback?** → **Callback deliveries are journaled effects: intent recorded before the attempt, at-least-once with bounded exponential retry, receiver-side dedupe on a delivery id, and exhaustion recorded but never the execution's failure.** Owner ratification (2026-08-28). The delivery id derives from `execution_id` + event ordinal — the execution-derived idempotency-key rule's next application (detach sinks 5.6, event dedupe 5.11, store writes 5.7). Retry is bounded — exponential backoff, on the order of five attempts across fifteen minutes, the exact schedule stated normatively in `docs/durability.md` — because a webhook is a courtesy the status route backstops, not a contract worth an unbounded queue. A `serve` restart resumes undelivered notifications from the journal like any other unfinished effect (resolved q28), and a re-parked wait whose parking webhook was already delivered does not re-fire it. One consequence is stated where a receiver meets it: retries mean a parking webhook and a settle webhook can arrive out of order, so receivers order by event ordinal, never by arrival (resolved q26–q29, 5.11).

36. **What of §7 M3's trigger line does the http-native events pass ship?** → **q32–q35 exactly; webhook-style events are `http` triggers and get no new trigger kind; `schedule` and queue-backed `event` triggers stay reserved for the sources HTTP cannot speak for.** Owner ratification (2026-08-28). A push-style event source is something that POSTs: with inbound auth (q32), outbound identity (q33), lifecycle webhooks (q34) and durable delivery (q35), the `http` trigger *is* the webhook story end to end, and an `event` trigger kind for webhooks would duplicate it under a second name. What HTTP cannot absorb is a **pull** source — a queue or pubsub system where nobody calls you, and a consumer loop must own ack/nack, redelivery and dedupe — and a **clock**, which has no caller at all. So the reserved kinds keep exactly those jobs: the settled `event_sources:` plugin design (5.11) stands as design, its Redis Streams reference backend leaves this pass's scope, and `schedule` waits behind it — kept, per the owner's call, for the pubsub systems worth supporting when one is actually needed (5.11, §7 M3).

37. **What is the topology of a distributed graph?** → **Hub-and-spoke: one hub owns the graph — scheduler, journal, wait board, triggers — and workers execute the nodes placed on them, dialing out only.** Owner ratification (2026-08-29). Outbound-only dialing is the clause that makes personal machines first-class: a Mac behind NAT with a dynamic IP joins the way a CI runner joins, and a placement therefore never needs an address (resolved q38). Peer partition — each machine owning a subgraph and its own journal — is rejected for the complexity it imports (distributed replay, split brain, cross-journal identity) against resilience nobody asked for. **The unit of horizontal scaling is the execution, never the node**: executions share nothing by construction (global-scope stores are already external backends), so scale-out later is sharding executions across hubs over the Postgres journal slot (resolved q27), while one execution lives entirely on one hub, always. Hub load scales with effect throughput and live state size, not with graph definition size — the heavy work happens on workers — so the walls are journal growth (compaction stays the named q28 exclusion), fan-out state in hub memory, and one JS event loop serializing large states; hundreds of concurrent executions are comfortable, and the answer past that is more hubs, not a smarter one. The cloud shapes (k8s, ECS) are the same topology with workers that never sleep on a flat network (5.10, §7 M3).

38. **How does a machine become a placement?** → **Placements stay logical names in the deploy layer; a worker claims them at an authenticated join, and addresses appear in no spec file.** Owner ratification (2026-08-29). `agent-compose worker --join <hub> --claims mac,gpu` — the claims are the deploy layer's placement names, the join is authenticated by a deploy-target join token (`${ENV}` reference only, the q32 credential posture, one kind: bearer), and several workers claiming one placement form a pool the hub dispatches across. Which physical machine satisfies a claim is decided by whoever shows up: placement is **capability affinity** — the machine with the signing keys, the GPU, the one licensed tool — not load assignment, which is why the binding surface is a label a worker asserts rather than an address a spec must know. **The v1 trust model, stated plainly: holding the join token is being trusted with the mesh** — the whole artifact (resolved q40), the right to claim any placement, and the journal's effect stream (resolved q42). A manifest check at join is self-reported presence, not authenticated capability, because proving a secret would mean sending it, which resolved q41 exists to forbid; per-placement credentials are an additive later hardening, not something the single token pretends to be (5.10, resolved q37, q41).

39. **What happens to a placed node with no live worker?** → **It parks: a third kind of wait on the existing board — journaled, restart-surviving, status-visible — and the wake is a worker join.** Owner ratification (2026-08-29). Parking writes the same deterministic wait identity human waits carry (node path + ordinal, resolved q4/q20); a joining worker's claims are scanned against open placement-waits and dispatch resumes in park order — the same scan-and-resume that recovery (resolved q28) runs for human waits and q35 runs for undelivered callbacks, and no polling anywhere. Heartbeat loss re-parks what was queued to the vanished worker. A parking can fire the `parked` lifecycle webhook (resolved q34), so a subscribed system learns "waiting for the Mac" the way it learns "waiting for a human". Bounding needs no new grammar: the node's `timeout:`/`on_error:` chain applies from dispatch, so "fail if the machine is not up in ten minutes" is already spellable. A closed laptop is a pause, not a failure — for the **undispatched** case, which is what parking is: a disconnect *mid-node* is an attempt failure resolved q42 governs, so a placement worth sleeping on wants a `retry:`. That pause is the payoff of sequencing durability first (5.5, resolved q26–q28, q42).

40. **How does code reach a worker?** → **The hub ships the whole generated artifact at join, pinned by artifact hash and compiler version in the handshake; a mismatch is a refused join naming both.** Owner ratification (2026-08-29). Workers hold no checkout and no YAML; redeployment is automatic on the next join or push, and version skew is a refusal rather than a drift. Workers need Bun, and the handshake says so — a scoped exception to resolved q18's Node fallback rather than a contradiction of it: the worker is a surface *around* the artifact, which is q18's own reading of where the fallback stops, and pinning one runtime keeps the handshake a single (artifact hash, compiler version, runtime) triple instead of a matrix; the fallback remains the story for a generated project someone runs by hand. Per-placement artifact *slicing* — a worker receiving only its own nodes' code and prompts — is deferred, named: on a personal mesh every machine is the owner's, and slicing is an optimization with a real complexity bill (5.12, resolved q38). *Amendment (2026-08-30), surfaced by the protocol document's gate on this entry: the entry's own clauses collided — "a mismatch is a refused join naming both" cannot hold of the artifact hash while "redeployment is automatic on the next join" holds at all, because the hub is the hash's source of truth: an unfamiliar or absent hash is a worker that needs the current artifact, and an absent hash is a cold start, which a refusal would lock out of the mesh entirely, since fetching is downstream of the join that names what to fetch. The mismatch clause therefore reads on what the worker **runs**, not what it **holds**: a compiler-version or runtime mismatch is a refused join naming both sides; an artifact-hash mismatch is repaired — the join succeeds and its answer carries the current artifact to fetch. `docs/distributed.md` §4.1 states the wire.*

41. **Where do secrets live in a distributed run?** → **Each worker satisfies its own placement's env manifest locally; the hub holds only its own; spoke secrets never transit the wire.** Owner ratification (2026-08-29). The per-placement manifest is computable statically — placements bind nodes, nodes bind env references, and the `References::of` walk already collects them — so a worker claiming `mac` without `SIGNING_KEY` set is refused at join with the variable named, the same posture the serve launch check takes (resolved q32). This is §7 M3's least-privilege line landing in its sharpest form: blast-radius containment falls out of the manifest, because the hub cannot leak what it never held — containment of **secrets**, precisely; mesh *membership* is resolved q38's single-token trust in v1, and the two claims should not be read as one (5.7, 5.10).

42. **Where do remotely executed effects get journaled?** → **In the hub's journal, single writer preserved: workers stream effect records home as they execute.** Owner ratification (2026-08-29). SQLite stays valid for the personal mesh because there is still exactly one writer; Postgres remains the multi-instance slot (resolved q27). A disconnect mid-node fails that node attempt under `retry:`/`on_error:` like any execution failure; a redispatch hands the worker the node's journaled effect history and the worker replays to the frontier — the q26 replay discipline extended over the wire. Dispatch is at-least-once with idempotency keyed by the execution-derived rule (its next application after detach sinks, event dedupe, store writes, and callback delivery), so a redelivered dispatch re-issues nothing the journal already holds (resolved q26, q35).

43. **RemoteGraph, or our own dispatch protocol?** → **Our own: a small authenticated persistent connection — join and claims, artifact handshake, dispatch, effect stream, heartbeat — on the serve surface. This supersedes §7 M3's and §5.10's "via `RemoteGraph`" wording.** Owner ratification (2026-08-29). RemoteGraph puts the seam at a served subgraph boundary: one opaque effect from the hub's view, so replay-to-frontier dies at the boundary unless the remote keeps its own journal — two journals, which is resolved q37's rejected shape; a `human` node inside a remote subgraph would interrupt on the remote's checkpointer, breaking wait-board unity for the same reason resolved q26 rejected the checkpointer outright; placements would force per-machine subgraph compilation, so a deploy-layer edit would restructure the compiled graph; and RemoteGraph dials hub-to-worker — inbound into a home network, the exact problem outbound dialing exists to avoid. The honest cost is owning protocol code instead of borrowing battle-tested plumbing; the mitigations are that the protocol is small and its hard semantics — idempotent delivery, journaled effects, replay — are machinery this project has already built and adversarially hardened twice. LangGraph remains the per-process execution engine on both sides (5.10, resolved q26, q37).

44. **What does v1 distributed ship, and what may it never foreclose?** → **The `worker` verb, live `placements`, park-on-unclaimed, the artifact handshake, per-placement env manifests, and hub-journal effect streaming — workers on Linux and macOS (owner call, 2026-08-29: Windows stays deferred) — under the standing constraint that nothing in v1 is a one-way door against HA.** Owner ratification (2026-08-29). K8s and ECS are a documented recipe, not an integration: a container running `agent-compose worker --join …` is the entire story — no operator, no CRDs, no second control plane to drift against the first. Out, named: multi-hub, worker-to-worker edges, per-placement artifact slicing. **The hub is a singleton by deployment choice, not by design assumption**, held by four invariants: (1) the journal is the complete hub state — any process pointed at it recovers every execution, which the crash/resume acceptance tests already prove and which *is* the failover primitive; (2) the worker protocol is reconnect-native with no privileged first connection — workers address a hub *name*, every reconnect re-handshakes, and all dispatch state re-derives from the journal, so replacing the hub process under a stable name is invisible; (3) single-writer-ness is the journal backend's lease, never a protocol or filesystem assumption — and the lease's **granularity is an execution set, not the journal**: SQLite's file lock grants the whole journal as one set, the Postgres backend (resolved q27's slot) must offer per-execution or per-shard leases before multi-hub exists, and effect-record identity is already execution-scoped, so no schema or protocol may assume one writer per journal — the assumption that would make q37's execution-sharded scale-out a migration instead of "run more hubs"; (4) ingress is name-addressed and execution-keyed — URLs derive from a configurable public base and routes resolve ownership through the journal, so a load balancer in front of one-or-many hubs changes nothing about what a URL means. HA later is running the standby and arbitrating the lease, not a rewrite (§7 M3, resolved q37, q42).

45. **May a placed component reach a `store.*` on a process-local backend?** → **No: `validate` refuses it, in any target whose deploy layer declares placements.** Owner ratification (2026-08-31: "refuse it at validate — a mesh with silently forked state is exactly the class of bug this compiler exists to make unwritable"). A `memory`, `sqlite`, or `local_fs` store is opened by the process that runs the component reaching it, and a mesh runs such a component in more than one process by design: several workers claim one placement (resolved q38's pools), the hub dispatches whatever else reaches the store, and each process opens **its own copy** — a write on one side is never a read on another, so state forks silently while the flow carries on. The rule reads on **execution, not membership**, the same way the env partition does (resolved q41, `docs/distributed.md` §9.1): a store on a process-local backend is refused when any component that can execute in a placement's process — a member, or anything reached through attachment (grammar §14.1 rule 4) — binds it. It refuses at **every store scope**, because even an execution-scoped store spans processes the moment its component does; and under `--target local` too, where a hub and its workers are separate processes on one machine. A composition with no placements, or a store reached only by components that execute on the hub alone, is untouched — one process may keep local stores. The repair an author writes is the one that already works: bind a networked backend, whose variables §9.1's partition already carries to every placement that reaches it.

46. **What does a `human:` node reached by a placed component mean?** → **A pause is a dispatch's third ending: the worker settles it *paused*, the wait lands on the hub's board like any human wait, and the answer re-enters dispatch with the pause in its history.** Owner ratification (2026-08-31: option (a), "add a third terminal outcome to the wire"), chosen over a static refusal because "the signing machine pauses for approval" is a legitimate mesh shape — the machine holding the capability is exactly where an approval-gated node runs. Mechanism, held to the standing disciplines rather than adding new ones: the result route (`docs/distributed.md` §3.4) gains a *paused* outcome carrying the node's deterministic wait identity (grammar §9.4) and its interrupt payload; the hub journals it and plants the wait on the one board — wait-board unity, resolved q43's ground, is preserved because the board never leaves the hub — and the dispatch is settled, so the worker is free and a worker gone between pause and answer costs nothing. An answer resumes by the replay discipline of resolved q42: the answer is journaled as the pause's effect record, the node re-enters dispatch — parking if nothing claims the placement (resolved q39) — and the redispatch's `effect_history` carries the answered pause, so replay-to-frontier consumes it and the node goes live past the point it paused, re-issuing nothing already paid for. A placed `human:` node must mean what the same node unplaced means: timeout/retry/on_error semantics, status visibility, lifecycle webhooks and the resume surface are the single-process ones, reached over the wire. This is a wire addition an older peer would misread as a failure, so it bumps `PROTOCOL_VERSION` per `docs/distributed.md` §10.3 — cost-free in practice, since the handshake triple already refuses mixed releases.

47. **Where does the boundary between generated and authored code live in an emitted project?** → **The manifest is the boundary, not a directory.** Owner ratification (2026-08-31). `build` already enumerates exactly what it wrote (`ARTIFACT_FILES`, `manifest.json`), so it overwrites and `--check`s precisely its own list, refuses to emit a name an authored file holds, and never touches anything else under `src/`. The flat `src/` layout stays — no `src/generated/` migration, no golden churn from moved files; `src/tools/` is the *conventional* authored zone the scaffold uses, but the machine answer to "who owns this file" is membership in the manifest. **Manual sections inside generated files are rejected**, named so the pattern is not re-proposed: `/** Begin Manual Section **/` markers make `build` a read-modify-write of its own previous output rather than a pure function of the spec, which breaks byte-identical goldens (§9.15's backbone), splits file identity between a `--check` checksum over generated spans and the artifact hash over whole bytes, and makes marker drift a silent way to lose user code — the sharpest hazard for the autonomous-agent workflows this project is built for. The ergonomic need behind them is met by resolved q48's stub-once scaffolding plus generated typed interfaces (5.12, resolved q40).

48. **How does a composition declare a hand-authored tool implementation, and what holds its contract?** → **A third implementation binding beside `exec:` and `http:` — a module binding naming a TypeScript file in the authored zone (`module: ./src/tools/sign.ts`) — with the type-checker as the merge tool.** Owner ratification (2026-08-31). Until now custom logic lived entirely outside the project: an `exec:` tool wraps whatever binary the machine has, and what that program does "is nobody's contract" (grammar §6.1, D24); a module binding is the first authored code *inside* the project, under a compiler-checked contract. The generated side emits, from the tool's declared `input:`/`output:` schemas, a typed interface the module must satisfy and the one registry seam that imports it; `tsc` — already a gate for every golden — holds the contract, so a schema change fails the authored file with a precise type error rather than a marker merge. `validate` refuses a binding whose file is missing, with the diagnostic naming the repair; `build` scaffolds an absent referenced module **once** — full typed signature, doc comment, TODO body — and never rewrites it again. Import direction is a rule: authored code may import generated modules (types, runtime helpers); generated code reaches authored code only through the registry seam.

49. **How does authored code travel a mesh, and where do its env references and dependencies live?** → **Spec-referenced authored files join the artifact list and its hash; what static analysis cannot walk — env and dependencies — is declared in the YAML.** Owner ratification (2026-08-31). A module-bound tool executes wherever its tool executes — on a worker, when placed or reached through attachment (resolved q45's executes-in closure) — and workers hold nothing but the artifact (resolved q40). So the artifact's file list widens from "what `build` wrote" to "what `build` wrote plus the authored files the spec references": a referenced module ships hash-addressed like everything else — editing a tool implementation changes the artifact hash and reaches every worker through the join handshake with no new machinery (`docs/distributed.md` §4) — while unreferenced scratch files in `src/` ship nowhere. Because `References::of` cannot statically walk `${ENV}` uses inside arbitrary TypeScript, a module binding declares its environment in the YAML exactly as `exec:` tools do (grammar §4.3), keeping resolved q41's per-placement manifest and q45's store rule sound over authored code. **Dependencies follow the same principle** (owner amendment, raised as "does the worker need to bun install?"): a module binding declares its npm dependencies in the tool YAML, `validate` requires **exact versions** — the artifact ships no lockfile, since a lockfile is what install produces rather than what build writes, so exact pins are what keep the hub's install and every worker's install resolving the same tree — and `build` folds them into the generated `package.json`, which stays pure-generated (resolved q47), makes a collision with the runtime's own pins refusable statically, and redeploys workers on a dependency change through the hash. The install half already exists: a worker's provisioning cycle runs `bun install` at materialise (`docs/distributed.md` §4 step 4).

50. **A trace sink: ship every execution's trace to a configured URL?** → **Yes: `trace_sink:`, a deploy-layer URL every settled execution's trace envelope ships to, on the delivery machinery the project already has.** Owner ratification (2026-09-01). Today traces are pull-or-per-execution — `run --format json`, the trace file, `GET /executions/:id`, the per-execution `callback:` — with no surface a collector can rely on; `trace_sink:` (a deploy-layer key beside `storage_backends:`) closes that. Delivery is at settle, through resolved q35's journal-backed at-least-once machinery: bounded retry, ordered per execution, and never blocking or failing the run it describes — a sink outage costs deliveries a retry, never an execution. Outbound auth reuses resolved q33's signing (`bearer`/`hmac`); the SSRF allowlist is deliberately *not* required here, because the sink URL is operator-written config trusted like a storage backend, not a payload-derived address — the distinction `callback_allow` exists for. The sink credential is a deploy-layer variable and so belongs to the hub's env manifest (resolved q41). What ships is the trace envelope only: the journal's payloads stay home (durability §8). The sink applies wherever executions settle under a target that declares it — `run` included, not just `serve`.

51. **OpenTelemetry export?** → **Yes — hand-emitted OTLP/JSON for spans, no SDK, with the metrics door held open.** Owner ratification (2026-09-01: "Hand roll trace export, SDK for metrics"). An OTLP format option on the same sink surface (`trace_sink: { url:, format: otlp }`; `envelope` is the default): the hub maps each settled trace to OTLP/HTTP spans — the execution as root span, each entry a span identified by its instance path, attempts/model calls/tool dispatches as child spans with events, routing decisions as attributes, and flow-as-tool joins as **span links** (the trace format's instance frames were designed for exactly this join). The trace's §11 exclusions carry over unchanged, so nothing reaches OTel that the trace may not carry. The SDK tension resolves against the dependency: OTLP/JSON over HTTP is a stable spec the hub can emit directly, so the exporter is hand-written and held by a **conformance fixture corpus** (the CEL-corpus discipline applied to span output) rather than by a vendored SDK; docs name "point an OTel Collector at us" as the answer for protobuf-only vendors. Export is hub-side only — the hub owns the trace, workers stream collectors home already, so a mesh needs no per-worker OTel story. Two amendments make the door two-way: an inbound W3C `traceparent` on an `http:` trigger is honored as the exported root span's parent, so an embedded graph joins its caller's trace; and the exporter MUST mint W3C-shaped trace/span ids and stable resource attributes so a later, standalone `@opentelemetry/sdk-metrics` adoption — the owner's chosen path for metrics/logs signals, its own PRD question when metrics become a milestone — correlates on any collector without touching the span exporter.

52. **A forced structured-output call after a tool loop ends on an assistant turn — and strict Anthropic-compatible gateways refuse it.** → **The runtime always closes the tool exchange with one fixed user turn before pinning the output tool.** Owner ratification (2026-09-01, from a live 0.6.0 field report). The with-tools agent path (§9.14's loop) exits on the model's replayed answer, so the pinned structured-output request carried a history ending on an assistant turn. On the Messages wire a trailing assistant message *is* the prefill feature, and prefill combined with a forced `tool_choice` is a contradiction — "continue this assistant turn" against "your answer must be this tool call" — that `api.anthropic.com` happens to tolerate and stricter Anthropic-compatible gateways (Bedrock-style "conversation must end with a user message" proxies, the norm in enterprise deployments) refuse with a 400. The refusal is shape-determined, so the failover ladder replays it on every attempt — an accepted cost, noted rather than changed: a retry is cheap insurance and the ladder cannot know a 400 is deterministic. The repair is **unconditional, not a per-gateway capability flag**: after the loop's final assistant answer and before the pinned call, the runtime appends one fixed user turn — exactly `Now produce the structured result.` — on both wire surfaces. It is harmless where the old shape was tolerated, a *more* coherent conversation everywhere (the ask to emit the verdict becomes a real user turn instead of prefill), and deterministic; a flag would be a config surface operators discover at 400-time, against the lean posture (§9.13). The synthetic turn is request composition only — it never enters the agent's durable history or the trace. The tool-less path already ends on the user turn and is untouched. And the class of bug closes at the oracle: the mock provider's Anthropic wire now **refuses** a forced `tool_choice` whose messages end on an assistant turn, exactly as the strict gateway does — the suite tolerated the broken shape only because the mock was as lenient as `api.anthropic.com`, and a conformance oracle earns its keep by being the strictest wire the runtime must satisfy.

53. **How does structured output ride each provider wire as model generations shift?** → **Handled inside the provider integration — never a consumer surface.** Owner ratification (2026-09-08: "we should never expose this to consumers or expect them to know … handle on a provider by provider basis"). The tension q52 exposed: the runtime realizes an agent's `output:` contract through forced tool use (the synthetic pinned tool; `strict: true` on the OpenAI wires) — the only schema-guarantee mechanism the Anthropic wire offered when built and the least common denominator gateways pass through — while the Anthropic API now carries native structured outputs (`output_config: { format: … }`) and its newest model generation removes forced tool use outright (400), naming structured outputs as the replacement. The ruling closes rulings (a) and (d) in one stroke: **no YAML key, no capability flag, no shipped model table — the generated runtime owns mechanism selection per provider wire and discovers what the endpoint accepts.** Mechanics: each wire's composer has a preference order (the wire's native structured-output parameter first where the wire defines one, forced-tool-plus-strict as the ladder's other rung); a capability-shaped rejection — the recognizable 400s for an unknown native parameter or a removed forced `tool_choice` — falls back to the other mechanism within the same call, and the working mechanism is memoized per (provider, model) for the process lifetime, so only the first call of a pairing pays the adaptive round-trip: the accepted cost of asking nothing of the operator. A double refusal (both mechanisms rejected) fails the call with a diagnostic quoting both refusals verbatim — the operator learns the endpoint is unusable, not which knob to set, because there is no knob. Ruling (b): **yes — the trace's model-call records carry which mechanism answered** (internal but observable; two deployments of one spec may answer through different mechanisms and the trace must say so), a trace-format change made under docs/trace.md §10's discipline. Ruling (c): the mock provider models every endpoint personality — native-supported, native-rejected (lagging gateway), forced-tool-removed (newest generation), and the q52 strict-gateway shape — so both mechanisms, the fallback ladder, and the memoization are held by conformance rather than by luck.

54. **Model-authored execution: builtin bash and file tools for agents.** → **Yes — `builtin.bash` and `builtin.files`, both in v0, declared per agent, contained by a workspace, env-scoped by config, and recorded in the trace.** Owner ratification (2026-09-02: "having bash and file tools that most providers already support is incredibly important"; rulings a–d below). The owner's framing corrects an earlier instinct and becomes the doctrine: the validate-time schema rail on each tool call was never the load-bearing contract — **the agent node's boundary is** (`input:` in, `output:` schema out, `max_tool_iterations` bounding the loop, the trace at the edges), and an agent that cannot adapt to its environment inside that boundary just pushes the work back onto humans. What these tools change is named honestly: every existing binding (`exec:`, `http:`, `module:`) fixes *what runs* at build time and lets the model fill schema-validated parameters; a builtin tool has the **model author the program at run time**. That is the same trust level `exec:` already extends to author-arbitrary binaries, extended to the model — the docs and `plan` output say so loudly rather than hiding it. The shape: (a) **both tools ship in v0** — `builtin.bash` (a shell session) and `builtin.files` (view/create/edit under a root), spelled as `builtin.*` entries in an agent's `tools:` list (ruling d) with per-tool config: workspace root (default a fresh per-execution directory; file operations that escape it are refused at run time), timeout, and environment. (b) **Environment is config-driven** (ruling b): a declared `env:` map exactly as `exec:` tools carry (grammar §4.3) — children run with a scrubbed environment holding only the declared vars, preserving resolved q41's per-placement manifests and q45's executes-in closure — plus an explicit config key to opt into inheriting the process environment for the machines where that is the point. (c) **The trace includes what the model ran** (ruling c): bash commands, their exit status, and file-tool operations are carried in the tool-call records — for these tools the model's program *is* the interesting record, so the trace's §11 posture gains a named carve-out for builtin tools; the change follows docs/trace.md §10's stability discipline. (d) **Per-wire declaration**: on the Messages wire the tools go out as the provider-defined tool types (`bash_*`, `text_editor_*`) so trained-model behavior engages; on the OpenAI wires (Responses where the provider speaks it per D122, Chat Completions otherwise) as equivalent function tools with our schemas; the conformance corpus and mock provider hold all surfaces. Session scope: one bash session per node activity, a retry restarts it (the ordinal-reset rule). Placement is the feature, not a leak: a placed agent with builtin tools executes model-authored commands on the worker — precisely what "the machine with the capability" placements exist for — so the tools join the executes-in closure like `exec:`; process-level containment remains §13's deferred row, not a v0 blocker. **Owner amendment (2026-09-07): this resolution SUPERSEDES resolved q31's builtin set.** q31 had already shipped author-bounded per-operation built-ins (`builtin.read_file`/`write_file`/`list`, grammar D123); implementation surfaced the collision, and the owner ratified full replacement — the builtin set is exactly `builtin.bash` and `builtin.files` (D123 superseded by D135, a migration diagnostic names where the old spellings' bounds moved). The accepted cost, taken knowingly: the old set's read-only granularity is gone — `builtin.files` is read-write within its workspace; a least-privilege `access:` knob is a future question if it earns one. The process lesson lands in CLAUDE.md: a spec for any new surface is drafted only after re-reading the full resolved-questions log for collisions, and must name every existing surface it touches or supersedes.

55. **A wire-unsupported schema keyword in a structured-output request — Anthropic's native decoder rejects `maxItems`, which D10 makes mandatory.** → **The wire schema is lowered per (wire, mechanism); the emitted parse keeps the full schema; the contract lives in the parse.** Owner ratification (2026-09-10, from a live field report; rulings a–d). The collision: grammar D10 requires `max_items` on every result-schema array (it is what bounds `over:` fan-out and keeps state finite), §3.5 maps it mechanically to JSON Schema `maxItems`, and the Messages wire's native structured-output decoder — the rung resolved q53 prefers — compiles only a JSON Schema subset that excludes array-length constraints, numeric constraints (`minimum`/`maximum`/`multipleOf`), string constraints (`minLength`/`maxLength`), and recursion. So nearly every real composition drew a 400 on the native rung — and correctly *not* a laddering 400: q53's recognizer refuses to read a schema-contents complaint as "this endpoint lacks the mechanism", because it doesn't — the schema as sent was never going to compile on that rung, and laddering would memoize a falsehood against the (provider, model) pairing. The rulings: (a) **each (wire, mechanism) pair carries a lowering table** — the constraint keywords its decoder does not compile — and the composer projects the emitted schema through it before the request; Anthropic-native strips the families above, OpenAI-strict keeps the `strictable` posture it has and gains its own table, and the mock provider's endpoint personalities enforce each subset so CI proves the projection matches the wire. The table is held on resolved q30's treadmill terms: a keyword a vendor starts accepting tomorrow is a table edit, never a grammar change, and lowering is per-keyword rather than all-or-nothing so the wire keeps every constraint it can compile. (b) **A stripped bound stays in the model's view**: lowering folds it into that schema node's `description` ("at most 20 items"), so the decoder stops enforcing what the model is still aimed at. (c) **Overflow is a parse refusal, nothing new**: an answer exceeding a stripped bound fails the emitted Zod parse — the same path any schema-violating structured answer takes today — and is never truncated to fit. (d) **The recognizer hardens in the same pass**: after lowering, a schema-keyword 400 on the wire means the lowering table is wrong, and it must surface as that call's failure — loud and unmemoized, never a ladder trip. The honest cost is a named **amendment to resolved q16**: constrain==parse equality now reads *the wire is constrained by the lowering's image; the parse checks the full schema* — equal wherever the decoder compiles the keyword, parse-only exactly where it cannot, the delta being the table and nothing else, still proven document-by-document in CI. The rejected alternatives: demoting array-bearing schemas to the forced-tool rung abandons q53's native-first for virtually every real schema, and relaxing D10 gives up the bound that `over:` dispatch is built on. What lands here is the pattern the provider's own SDKs apply — strip unsupported constraints from the wire, validate client-side — and the precedent this codebase already recorded once at `strict-is-refused-by-an-optional-property`: when a wire cannot express a schema feature, the contract lives in the parse (5.2, 5.9, resolved q16, q30, q53; grammar D10, §3.5).

58. **Does a coder node inherit its provider's connection — `base_url:`, credential, `headers:`?** → **Yes — an amendment to resolved q57(d) and grammar D141: the model's resolved provider connection facts cross the boundary, mapped by each driver into the harness's own connection surface through a curated per-harness connection table; a declared fact the harness has no slot for is a `validate` error naming it; a node `env:` colliding with a mapped variable is a compile error naming both sources.** Owner ratification (2026-09-17: "that needs to be configurable, ideally reusing the same primitives that we have for other nodes", ratifying rulings a–d). The gap was sharpest in the deployment resolved q25 exists for: a gateway deployment binds `provider.anthropic` with a `base_url:` and every agent node routes through the gateway, while a coder node on the *same model address* silently talked to the vendor endpoint unless its author hand-carried the gateway URL and credential in `env:` — per-node duplication in harness-native spellings, drifting, and a break of 5.9's "swapping hosted to a gateway is a one-line provider edit" promise (q25's whole point) for exactly one node kind. Rulings: (a) **the connection facts cross; the ladders still stop.** `base_url:`, the credential (with q25's keyless-gateway posture intact — an absent key maps to *no injected credential variable*, never an empty one), and `headers:` resolve through the model's provider and are mapped by the driver into the harness's own connection surface — for `cc` the Agent SDK's environment contract (its base-URL, API-key/auth-token, and custom-header variables), for `codex` its API-key and provider-base-URL config surface — every slot verified against the pinned SDK's `.d.ts` and documented contract exactly as q57 verified its API shapes, never recalled. Failover **routes** remain refused on a coder `model:` (D141's compile error stands — a ladder cannot reach inside a foreign loop), and q53's mechanism ladder and the rest of the connection's behavior stop at the boundary as before. (b) **The map is a curated per-harness table held on q30's terms** — a slot the vendor ships tomorrow is a table edit, never a grammar change — but with q30's warning tier hardened where q25 hardened it: a declared connection fact the harness has **no slot for** is a `validate` **error naming the fact and the harness**, not a warn-and-drop, because a fact that changes where traffic goes or whether it authenticates failing at run time instead of compile time is exactly the class q25 refused (G3). If a harness's SDK tier genuinely offers no slot for a fact (a header family, say), that narrowness is the table's honest content and the error's honest message — never a faked slot. (c) **One spelling per fact**: a node `env:` entry naming a variable the connection map would set is a compile error naming both sources — no silent shadowing and no precedence rule to memorize; an author who wants one node on a different endpoint defines another provider, the cheap move q30 already leans on. 59. **How does a generated project resolve packages through a private registry or mirror?** → **A deploy-layer slot, `package_registry:` — a `url:`, an optional `token:` (`${ENV}` reference only), and optional per-scope entries — and `build` emits `bunfig.toml` and `.npmrc` as pure-generated manifest members that spell the token as the env reference the installer expands at install time, so the secret never enters the emitted bytes.** Owner ratification (2026-09-17, from a live field report: a company-internal npm mirror was reachable only by post-processing the emitted project with a custom build script). The gap, stated where it bites hardest: a hand-placed `bunfig.toml` beside the emitted project survives locally — the manifest boundary (resolved q47) never touches it — but it is **not in the artifact**, so on a mesh every worker's `bun install` at materialise (resolved q49, `docs/distributed.md` §4) resolves against the public registry, which on the corporate network that mandates a mirror is exactly what is blocked; where a package resolves from is a placement fact, and placement facts belong in deploy files (5.10), which is the same sentence that placed the journal (resolved q27) and the trace sink (resolved q50). Rulings: (a) **the slot**: `package_registry:` sits in the deploy file beside `storage_backends:`, with `url:`, optional `token:` under the q32 credential posture (`${ENV}` reference only, never a literal), and an optional per-scope map (`"@corp": { url:, token: }`) because corporate setups routinely split scopes; the composition says nothing. (b) **`build` emits the config, both spellings**: a `bunfig.toml` and a `.npmrc`, pure-generated members of `ARTIFACT_FILES`/`manifest.json` (resolved q47 — a post-process script is never again the mechanism), the `.npmrc` covering resolved q18's Node/npm fallback so the emitted project installs against the mirror under either runtime. (c) **The token is a spelling, not a byte**: both files carry the environment-variable *reference* (`${VAR}` in `.npmrc`, Bun's equivalent form) and the installer expands it at install time — the secret never enters the artifact, the artifact hash (resolved q40) is stable across token rotation, and nothing secret transits the mesh (resolved q41's ground). Presence is the launch check's and provisioning's to verify (resolved q15's posture at the surfaces that install). (d) **Distribution falls out of existing machinery**: the two files ship in the artifact through the resolved q40/q49 hash handshake with no new protocol, and the token variable joins the env manifest of the hub and of every placement that materialises the artifact — resolved q41's rule reading on one more reference site, exactly as resolved q58 extended it to provider connections. (e) **Gates stay hermetic**: goldens pin the emitted config bytes for a mirror-shaped fixture; CI never installs against a private registry, and the compiler's own gate installs are untouched. 60. **Selecting a harness's own permission mode — and what a reserved `settings:` key does at compile time.** → **Two rulings: a first-class `permission_mode:` key on the coder block, per-harness, constrained to never widen what `access:` states; and reserved `settings:` keys become compile-time refusals — a new `reserved-harness-setting` diagnostic naming the key, the bound it would reach, and the first-class key to use instead.** Owner ratification (2026-09-18, from a live field report: a user needed the Agent SDK's `auto` permission mode, found the `access:` enum reaches only three of the SDK's six modes, and probed `settings:`/`extraArgs` as the workaround — which the q57 reserved lists rightly wall off, but with only a generic warning and a silent run-time drop, costing the user real investigation time; the probe is the evidence for both rulings at once). Rulings: (a) **`permission_mode:` is a first-class optional key on the coder block, never a `settings:` key** — a bound must be readable off the node that holds it (resolved q54's principle, the same reason `allow_tools:` and `access:` are keys and not settings), and q57(c)'s doctrine that `settings:` never reaches a bound another key states survives intact *because* the legitimate ask gets a key of its own. Per-harness closed set from a curated table on resolved q30's terms: `cc` carries the pinned SDK's modes; `codex` refuses the key with a diagnostic naming the asymmetry (their per-call approval axis lives in an app-server tier this project does not adopt — q57(c)'s stated posture). **The invariant is the widening bound**: a mode may never grant an operation the node's `access:` level's mapped default would refuse — `read_only` admits `plan` alone; `workspace_write` admits `acceptEdits`, `auto`, `default`, and `dontAsk`; `full_access` admits all six — the concrete admissibility table shipped as a compiler table (editable on q30's treadmill terms, verified against the pinned SDK's documented semantics exactly as q57/q58 verified their surfaces, never recalled) and the widening principle stated normatively in the grammar. 61. **A map over a coder node cannot actually run in parallel — every dispatch shares one `workspace:`.** → **Three rulings: `workspace:` becomes a runtime binding evaluated in the node's input scope per dispatch; the shared-workspace race becomes unwritable — a concurrently-dispatchable coder whose `workspace:` does not depend on the per-dispatch scope is a `validate` error naming the repair; and `workspace: fresh` auto-provisions a per-dispatch directory, deterministic by the instance path and clean per attempt.** Owner ratification (2026-09-18, from a live field report with the diagnosis attached: a PR-review graph fanned a map over a coder node and the dispatches clobbered each other's checkout, forcing serial execution — "the map's max_concurrency is a lie for coder nodes; anything >1 is a data race on the shared workspace"). The cause, named precisely: `workspace:` shipped as a grammar §4.3 class-2 binding — literal or `${ENV}`, resolved at compile/launch time — so it cannot read a per-dispatch state value, while an `exec:` tool's per-item working directory flows through input bindings and can. The whole point of a coding harness in a graph is fan-out (review N PRs, fix M files concurrently), and 5.6's instance-isolation doctrine — item-scoped context, per-instance history, §9.4 instance paths — stopped at the filesystem the harness touches. Rulings: (a) **`workspace:` moves to the runtime binding class** — an expression evaluated in the node's input scope at each dispatch, exactly as an `exec:` tool's arguments are — so a map item carries its own checkout (`workspace: item.worktree`) and `max_concurrency` becomes real for coding. Everything q57/q58 built downstream of the value is unchanged: the resolved path still feeds the same per-harness containment mapping (codex sandbox preset root, cc cwd/permission surface), mandatoriness stands, and `References::of` walks the expression so env manifests (resolved q41) and launch checks (resolved q15) keep holding. The one thing given up is stated: `validate` can no longer inspect the path's text, only the expression's well-formedness — which is the same trade every runtime binding already makes (grammar §4.1). (b) **The race the field report hit becomes unwritable, the resolved q45 posture**: a coder node dispatched by a map whose `workspace:` expression does not read the per-item scope is refused by `validate` unless the map's concurrency is 1 — the diagnostic names both repairs (bind the item's own path, or declare `max_concurrency: 1`) — and two coder nodes on statically-concurrent branches whose `workspace:` values are statically equal draw a warning naming both nodes (an error is withheld there because equality of `${ENV}`-bearing values is a launch fact, not a compile fact — stated rather than pretended). (c) **`workspace: fresh` is the batteries-included spelling**: the runtime provisions a per-dispatch directory under the execution's scratch (`.agent-compose/workspaces/<execution>/<instance path>`), named deterministically by the §9.4 instance path, created **clean per attempt** — a retry gets an empty directory, because a half-clobbered workspace is routinely why the attempt failed, and the journal's replay discipline is untouched since the workspace's contents were never the effect record (resolved q57(b): the answer is the structured output). This is resolved q54's fresh-per-execution default arriving at the coder node, and it satisfies (b) by construction. What `fresh` does not do is also stated: a coding task that needs a checkout still prepares one — an upstream `exec:`/`tool.*` step cloning or worktree-ing into per-item paths the map items then carry into (a) — because provisioning source control is a graph author's step, not a harness adapter's guess. Surfaces: the graph document's coder view shows the workspace expression (or `fresh`) — additive under `docs/graph.md` §9.2 — and the `HarnessRecord` gains the resolved path (additive, `docs/trace.md` §10.2), so a trace reader can see which directory a run actually held. Builds on q15, q22–q23 (diagnostic/doc binds), q41, q45 (the unwritable-race posture), q54, q57 (amending `workspace:`'s binding class, nothing else), q58; grammar §4.1/§4.3, §8.9, §9.4; PRD 5.6 (5.5, 5.6, G3).

63. **Postgres and MySQL `kv` stores go live — the first implemented arms of grammar 14.3's remote vocabulary.** → **Four rulings: the runtime's blanket refusal of non-local store providers narrows — `postgres` is implemented for the `kv` kind and `mysql` joins the vocabulary beside it (grammar §14.3's kv row, the `BackendProvider` enum, `opens_in_process` answering false for both), while every other remote provider keeps today's named refusal; the store contract the SQLite substitution already keeps is the contract the remote arms implement — schema-checked ops, scope semantics (`execution`/`session`/`global` keyed exactly as the local backend keys them), recorded reads for replay, and at-least-once writes deduplicated by the §5.8 execution-derived idempotency key, now enforced by the backend itself (a repeated write carrying the key the first attempt carried applies once, stated and tested rather than assumed of the caller); binding stays q9's alias-only shape untouched — `storage_backends:` aliases and per-kind `defaults:` in a named target's deploy file, `${ENV}`-only connection config, D87's `local` override unconditional — so this entry adds no grammar beyond the one vocabulary word `mysql`; and unlike the journal, a store is deliberately multi-writer — no writer guard, because grammar 14.1 rule 5 (q45, D131) already governs who may reach one, two processes reaching a dialled store are two readers of one store by design, and per-key last-write-wins is the stated concurrency posture.** Owner ratification (2026-09-21, in the same ratification as entry 62: "remote MySQL and Postgres for journals and other storage", split two ways so each lands behind its own review). What the arms inherit from entry 62 is deliberate and named: the same pinned drivers (`pg`, `mysql2`) carried only by targets whose bindings need them, the same dockerized conformance posture — the store contract driven against SQLite always and against real Postgres and MySQL service containers in CI, loud-skipped where the env URLs are absent — and the session hygiene its seven review rounds paid for (driver `error` listeners; byte-wise key collation, `COLLATE "C"` / `ascii_bin`, because a kv key that folds case corrupts; payload columns sized past 64 KiB; `ANSI_QUOTES` and `autocommit` asserted at session open; schema names qualified per database). Agent-attached tool synthesis (§5.8 mode 1) and store-op nodes (mode 2) are untouched — they call the same store interface and cannot tell which arm answered, which is the q27 phrasing applied to stores and the reason this is a runtime release and not a grammar one. 64. **Does a detached dispatch's work ever reach the trace system, or is it unobservable by contract?** → **It ships its own envelope: the trace sink contract gains a second event class — one POST per settled detached `flow.*` delivery — carrying that delivery's own full trace, and the parent's entry does not move an inch.** Owner ratification (2026-09-22, from a field report: a multi-minute detached coder review ran to completion, posted a real GitHub review, and left no trace anywhere — the parent's stub dispatch record was the whole account, and the only surviving evidence was journal effect rows and serve-log lines). The ruling's two halves, stated so neither is mistaken for the other: **what D94 settled stays settled** — the join counts a detached dispatch the moment it is issued, `attempts` is `0`, no outcome is ever observed by the parent, and the parent's trace entry carries exactly the stub `"detached"` record, because that entry is written when the join finishes and a fuller one would be nondeterministic (trace §5.1's rationale, which this entry re-reads as being about the *parent's entry only* — the one thing it was ever about). **What was never asked is now answered** — the delivery itself runs real nodes under the parent's execution id, past the join, under its own signal, and the runtime already knows the moment it settles (the quiescence mark that comes off when the delivery ends, however it ends); at that moment it ships an envelope of its own to `trace_sink:`: the delivery's entries in full — its model calls, store ops, tool loops taped per q57, its own joined dispatches — headed `detached: true`, `parent_execution` (the id it ran under), and the §9.4 execution-derived `idempotency_key`, which the trace document already blesses as the readable form of the flattened instance path, so the join between the parent's stub record and the child's envelope is string equality on the key. A delivery that *failed* ships too, outcome recorded — the debugging story is strongest exactly there — and rule 7 still holds: shipping is downstream of settlement and nothing about it can delay or fail the enclosing flow. Delivery of the envelope itself is the sink's existing best-effort POST contract, at-least-once across recovery (a `serve` restart that resumes a detached delivery re-ships on its settlement; receivers dedupe on `(parent_execution, idempotency_key)` — the §9.4 receiver-side rule's next application), and the §12 OTLP mapping gains the same head fields as root-span attributes. What this deliberately is NOT: a detached delivery does not become an execution — no execution row, no journal of its own (effects stay journaled under the parent id, q26/q29 replay untouched), no recovery identity beyond what §9.4 delivery recovery already gives it — because a second execution concept would ripple through the journal schema, quiescence and recovery for zero additional observability. No grammar moves: `detach: true` (D59, local-target-only), `trace_sink:` (§14.5) and the §9.4 carrier list are all unchanged — the idempotency key gains a *reader*, not a new carrier. Verification is ratified with the ruling: the mock-provider e2e drives a detached `flow.*` delivery to settlement and asserts the sink received two envelopes — the parent's, with its stub record, and the delivery's, with the linkage head and the inner trace — plus the failed-delivery case shipping with its outcome, per Validation strategy. Collision review: PRD 5.6 (fire-and-forget and the idempotency-key design — both halves untouched; the key does new duty), D94 (restated, not amended — its join semantics are the first half of this ruling), D59 (detach stays local-target-only, so the new event class exists only where detach does), D28 (admission — orthogonal), q26/q29 (journal and replay — effects stay under the parent id), q35 (the sibling at-least-once + receiver-dedupe delivery pattern this envelope's shipping follows), q57 (the coder taping that now has somewhere to land for detached reviews), trace.md §2 sink table / §5.1 / §7.2 / §8 / §12 (the surfaces that move: the sink table's "one POST per settled execution" becomes two event classes; §5.1 gains a forward pointer from the stub record to the child envelope; §8's key prose names the new reader), grammar §8.6 rule 7 (its "nothing it does can delay the enclosing flow instance" now has one more thing to be true of).
